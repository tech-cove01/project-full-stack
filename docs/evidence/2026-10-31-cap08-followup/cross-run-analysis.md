## 2. 跨时钟量化：正式2独有的MySQL时基拒绝不能覆盖旧B1

Windows间隔取两次 `globalStatus` 采集起止中点差；有符号差为 `MySQL Uptime增量×1000 − Windows中点间隔`。Uptime为整数秒，原helper的容差原样保留，未放宽判据。

该表与独立复算统一采用时间戳解析到微秒的口径；API uptime本身精度为毫秒，不把亚毫秒残差当作额外精度保证。完整capacity窗口含预热、stable和wrapper收敛，不能与上表stable附近的MySQL采样窗口直接相减。现有Windows观测没有约3秒墙钟跳变的证据；墙钟与单调钟同步前进仍不排除待机期间工作受抑制。5秒采样也不能排除样本之间的短停顿。

**MySQL Uptime不是Linux `/proc/uptime`，也不是CPU有效执行时长。** [8.4官方手册](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html#statvar_Uptime)只将它定义为server已运行秒数。核对[官方8.4.0标签的 `show_starttime`](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/mysqld.cc#L10242)，实际返回THD查询开始秒数减server启动秒数，启动值由 `time(nullptr)` 初始化；[同标签THD实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/sql/sql_class.cc#L3000)通过 `my_micro_time` 设置查询开始时间，[官方8.4.10头文件](https://dev.mysql.com/doc/dev/mysql-server/8.4.10/my__systime_8h_source.html#l00182)的非Windows分支使用 `gettimeofday`。因此这里比较的是guest Epoch墙钟秒进度，不能仅由短差推出VM暂停。本次没有确认旧容器实际二进制对应的8.4补丁版本；这些链接用于8.4系列实现边界说明，不冒充该二进制的逐字节来源证明。

旧访问快照仅记录Redis `INFO commandstats`，没有Redis服务器uptime/time；capacity中的Redis字段也是连接池统计。不存在可用于此窗双依赖时钟交叉验证的Redis uptime，不补造该数据。

## 4. 宿主事件增强了正式2的解释，仍保留具体机制边界

宿主原生日志审读取得正式2同窗Kernel-Power 506@14:02:49.0378364、507@14:02:52.4047896 UTC，进入/退出待机，Reason=Lid，进入时 `LidOpenState=false`、退出为true，区间3.3669532秒。退出原始字段另记 `SleepEntered=true`、`DurationInUs=3368132`、`SleepDurationInUs=2361858`；这些不同口径不替换成同一个“暂停时长”。该区间位于前一正常capacity与末异常capacity附近，并在native dropped早停前。Windows中点间隔164.1015秒扣该事件边界区间为160.7345468秒，与MySQL Uptime+161秒仅差265.4532毫秒；这一算术落在整数秒与采集不确定性范围内，增强环境干扰解释的时间相容性，并不证明该区间造成了全部时基差。

它不是VM暂停时长的直接测量。末次API capacity时间14:02:52.0422603甚至位于506/507边界内；待机区间不能表述成所有Windows/VM/容器进程完整停顿3.3669532秒。现有容器restartCount0、OOMfalse仅排除记录范围内对应容器重启/OOM，不证明没有guest时钟变化、低功耗工作抑制、网络/依赖等待或API竞态。

宿主审读还查询旧B1的11:20:28—11:20:38、A2的11:22:29.260—11:22:34.700窄窗，各向两侧扩展2分钟，以及诊断1/正式1整个stage各扩展2分钟，均未找到此次选取的506/507/566三类事件。这个有限查询不排除其它宿主扰动或日志留存边界；不能把正式2有Lid事件迁移成旧B1已归因，也不因旧窗0事件就证明宿主全程无停顿。

## 5. 最小区分预测与收尾风险

复现不稳的已知事实是同46源码/同fixture/同生成器设置下正式1通过、正式2失败，且正式2存在确切Lid待机同窗事件。它支持间歇性外部条件会影响本地容量结果；尚无证据把所有历史长尾归为一个确定业务机制。旧B1冷填充排队、A2无cards池等、正式2热阶段池等不能仅凭共现合并成一条因果链，也不能据多个通过轮证伪低概率业务竞态。

本次第二轮以既有宿主事件对齐为止，**无需为了用满“轮数”再发新负载**。若未来另有授权且必须区分残余机制，最小观察应保持同源码/同负载，用一个共同时间轴同时保留：宿主原生电源事件、Windows墙钟/单调发收时间、两依赖独立存活及服务器墙钟、API活动阶段/池状态和生成器调度。其可证伪预测分别是：

1. 宿主/虚拟化或共同链路干扰：独立依赖及多个API阶段同时延迟，且与宿主事件或guest时钟异常同窗。只有MySQL Uptime短差不充分。
2. API业务/池/驱动等待：宿主与独立依赖保持进度，但API特定阶段活动年龄/栈先增长；需抓到等待位置，不能从全池累计值推出。
3. 生成器自身调度：生成器发起落后/VU分配异常先出现，而同期独立API阶段和依赖保持正常。当前服务端两池等待也增长，因此不能只凭dropped判生成器单因。

它们是未来观察设计，本文未执行，也不把未来通过作为当前正式组补轮。

风险按实际交付边界判断：

| 发现/状态 | 对收尾的影响 |
| --- | --- |
| 已证权限越界、错误内容/个人状态污染、持久化不一致、不可收敛死锁或泄漏 | 功能/发布阻断，应小修并验证；本次只读证据未建立此类P1/P2 |
| 原定100/s稳定组的unknown、drop、发起/成功率或延迟判据失败 | 容量验收阻断，原因归为环境也不能改原失败；当前仍属此状态 |
| 功能独立核验成立，发现本地宿主待机干扰，残余历史长尾仍未知 | 可冻结功能并完成源码讲解、材料和正常功能演示；公开容量/SLA结论保守，注明环境与未通过项 |
| 两轮有限排查后没有进一步可证机制 | 保留已知/未知并停止；不盲调池/TTL/deadline，不自动扩功能或续无限排查 |

建议收尾口径为“功能已核验并冻结；CAP-08稳定容量未通过；正式2有Lid待机同窗证据，具体guest/依赖传播机制未测；旧B1仍未知”。这允许功能版收尾，不允许写100/s重复稳定、性能整组通过或原事故已修。
