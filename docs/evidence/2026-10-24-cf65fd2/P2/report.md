## 负载模型与修正

第一轮使用 `per-vu-iterations`、200 个 VU 同时建连。结果：100 个请求成功受理、100 个请求在 TCP 层被拒绝（k6 记录 connection refused），`http_req_failed` 阈值未通过。活动 `1018` 最终 100 笔订单、库存 0，说明成功进入服务端的请求仍保持正确性，但该轮不能作为正常吞吐结果。

疑似原因是 200 个瞬时连接超过嵌入式 Tomcat 的 accept 队列/Windows backlog，本次未进一步定位。后续业务场景改用：

- **20 VU × 10 轮**（共 200 个不同账号、每个账号一次）验证库存与订单正确性；
- **20 个并发**验证同一账号重复请求；
- 单独用暂停消费者 + 重启验证 Stream 恢复。

首轮 200 同时建连的数据保留为“负载模型/接入层限制”的证据，不混入下面的业务结果。

对账：`0 + 100 = 100`，通过。原始摘要：[k6-multi.json](k6-multi.json)。

### 2. 同账号重复请求（活动 1019，库存 100）

| 指标 | 结果 |
| --- | --- |
| 负载 | 20 个并发请求，同一账号、同一活动 |
| HTTP 200 / 429 | 5 / 15（限流 5 次/秒/用户） |
| 业务成功响应 | 5（均为同一订单 ID 的幂等返回，不是 5 笔新单） |
| 新订单 | 1 |
| DB/Redis 库存 | 99 / 99 |
| 唯一 user / 订单 | 1 / 1 |

对账：`99 + 1 = 100`，通过。限流生效，且没有第二笔订单。原始摘要：[k6-duplicate.json](k6-duplicate.json)。

### 3. 消费者进程重启（活动 1020，库存 20）

1. 调用 dev-only `POST /dev/consumer/pause`，等待消费者退出读取；
2. 20 个不同账号抢购，全部受理；DB 订单 0，Stream lag 20；
3. kill 后端进程并重启；
4. 恢复后 20 笔订单全部创建，DB/Redis 库存 0，pending 0，死信 0。

结果：`0 + 20 = 20`，通过。原始摘要：[k6-restart.json](k6-restart.json)。该场景验证“已受理但尚未投递给消费者”的消息在进程重启后不丢失；不等同于 ACK 前崩溃窗口。

### 4. pending 消息接管（活动 1022，库存 3）

1. 暂停真实消费者；
2. 受理 1 个预约，并用 `XREADGROUP ... fault-consumer` 将消息投递给一个不 ACK 的假消费者；
3. 此时 `XPENDING stream.orders g1` = 1，DB 订单 0；
4. kill 并重启后端；新消费者在空闲阈值后 claim 该 pending 消息；
5. 订单 `652324529179197923` 于 21:13:29 创建，status=1；DB/Redis 库存 2；pending 0，死信 0。

结果：`2 + 1 = 3`，通过。该场景覆盖“消息已投递、未 ACK、消费者退出”的恢复路径，但没有覆盖“DB 已提交、ACK 尚未发出”的精确窗口，也没有制造 DB 提交结果未知的情况。

### 5. 补偿重试与缺键（复用 P1 证据）

- 取消补偿事件重复投递：Redis 库存保持 3，`comp:done` 去重键存在，未二次增加（P1-7）。
- 删除库存键后重投同一事件：outbox 进入 `NEEDS_REVIEW`，没有用 `INCR` 创建虚假库存；恢复库存键后人工置回 DONE。
- 旧的开闸事件在下架后重放：gate 保持 `CLOSED/2`，未重新开放。

## 限流口径

- 本次实现为 Redis 固定窗口：抢购每用户 5 次/秒，核销每用户 10 次/秒，窗口 2 秒过期；多实例共享 Redis。
- 429 单独计数，不混入库存不足/重复请求。
- 固定窗口有边界突刺；Redis 不可用时当前实现 fail-open，交易链路仍会因 Lua 依赖失败而拒绝，不能把 fail-open 当作可用性保证。

## 结论

在单机、单实例、本机同机压测条件下：

- 200 个不同账号争抢 100 库存，最终 100 笔订单、0 超卖、0 重复、0 系统错误；
- 同账号 20 并发只产生 1 笔订单，15 次 429，库存只扣 1；
- 消费者进程重启后，已受理未投递的 20 条消息全部成单；pending 消息在空闲阈值后能被新消费者接管；
- 取消/退款补偿重复投递不会重复回补，库存键缺失会保留待核对事件。

这些结论不外推到生产容量、多实例或 Redis 故障切换。
