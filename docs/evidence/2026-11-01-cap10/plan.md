## S1前固定的夹具初态与窗口隔离

512个合成独占关系在prepare时显式预置inactive/version0（数据库schema允许，尚无业务迁移/事件），不是已测写吞吐。每个短窗、候选和正式窗执行同一准备顺序：有限10秒warm单列→SQL/Redis合成夹具归一化→最多60秒准备排空/核验→重新读取稳定前RR→主窗口。归一化只把实际active1关系转为0：版本单调加1、规范false事件与公开计数在同事务，原业务Mark Lua按最新版本补派生，清理本组计数键并等待既有本地TTL失效；不倒退版本、不删除历史、不发额外API重置负载，不修改TTL/业务代码。

稳定前必须512关系都existing/active0、每笔记计数0、Redis集合/版本符合事实，全部setup事件已Done/三组IGNORED且无lag/停车，再重取native输入。setup SQL/Redis动作、版本/事件增量和耗时全部单列，不纳入HTTP或mutation主窗分母；准备未知/不一致即停批，warm一旦启动已消费名额。H1/H2初态的active/existing/独占关系分布相同，绝对version及累计事件表规模继续增长并公开归档，不声称数据库字节完全相同。该准备行为在S1前冻结，诊断与同率优化对照也一致采用，不把初始insert/update差异冒称优化收益。

## 2026-11-02 消费者同步 Offset 微批

用户后续明确取消本批工时、优化次数和窗口数上限，继续同次云环境取得结果；原失败证据和业务正确性、稳态、持久化判据保留。S8 在 relay=8、400/s×60s 下完成24000次真实变更，API P95/P99=95/142ms，但三组收据末15秒仍净增长，恢复32.65秒，分类为有效性能受限，作为下一同400/s对照的基线。

本小票只合并成功 LIKE 的同步 OffsetCommit：`GO_COMMUNITY_CONSUMER_COMMIT_BATCH` 默认1，严格1..64，本批显式32。每条仍独立严格解码、校验源 Key/Header、业务哈希与控制 fence，逐条提交原 DB 收据事务后才进入有界待确认前缀；Kafka `CommitInterval=0` 不变。无确认的整批原样重试，不重做已证明的 DB 效果、不继续 Fetch。非LIKE、非法事件和持久停车先同步确认旧前缀，再按原单条处理与确认，不能跨过缺口。

首条 DB 已提交后，以10ms限制继续取消息组批的等待；每条 Apply/Park 的独立5秒期限及同步 OffsetCommit 的5秒期限不变，10ms不是整个批次的硬执行时长。取消和退出留下未确认前缀供原持久幂等收据重放。Go/SQL/Redis配额、relay=8、Kafka同步生产确认及收据SQL保持不变。验证覆盖未知ACK重试、取消、低流量组批、有效非LIKE隔离、坏源Key/Header停车，以及隔离库/自有Kafka主题中先持久收据、ACK失败、重启重放的有限集成；先同400/s对照，再按实测定档，不预报收益。

## 2026-11-02 LIKE IGNORED 收据事务微批

S9同400/s完成24000次真实变更、无未知/无操作/HTTP错误，但保留1次发压时序违规，原分类为发压器受限；三组收据末段仍净增长，不能据此宣告容量通过。同步Offset合并没有消除逐条收据事务的固定开销，下一小票沿用默认1/显式32的配置，三组processor增加仅LIKE的可选原子收据接口。

worker在最多32条、首条取到后10ms的有界取消息窗口内保留完整原始LIKE前缀，随后逐条执行原严格Envelope/源Key/Header检查，再用一次RC事务共享该projection原控制行锁（follow/feed原FOR SHARE，search原FOR UPDATE），批量写唯一IGNORED收据并在同事务逐一核对全部event_id/hash/state。只有整个DB事务确认成功才同步提交对应Kafka前缀；ACK未知只重试ACK。非LIKE保持原单条屏障；批事务失败或取消保留全部raw，后续按原逐条Apply/重试/Park/单条ACK处理，不跨未确认缺口。收据内容、重建fence、幂等冲突、生产确认和持久化均不放宽，只有事务固定开销被合并。10ms仅取消息组批，整批DB事务仍独立5秒；有限真实集成验证原子回滚、旧hash/state冲突、重建锁阻挡、唯一收据和ACK失败后重启重放。负载和源码对照逐窗记录，不预写通过或提升比例。

## 2026-11-02 Claim 释放未匹配活租约的扫描锁

独立登记的空集成库使用真实 `Repository.Claim`，预置未到期 PROCESSING 头行和到期 PENDING 尾行；仅通过 GORM Trace 在真实锁定 SELECT 返回后、事务提交前暂停。原代码继承会话 RR 时，另一 owner 的 `Done` 对未匹配头行阻塞超过500ms，释放 Claim 后503.632ms才完成；只将该会话预设为RC的对照，`Done` 在 Claim 仍暂停时1.164ms完成。原红回归和两种会话预设均保留，不以此冒称吞吐已提升。

本小票仅为 Claim 的事务显式指定 `sql.LevelReadCommitted`，释放扫描后未匹配的活租约行锁；原 active 索引、OR到期条件、ID顺序、SKIP LOCKED、30秒租约、attempt fence、重试与同步生产确认不变。真实回归要求两种会话预设下均能在 Claim 提交前完成旧 owner 的 Done，另重验既有到期资格/跳锁和8路64事件无重复收敛。主业务事务及 MySQL 全局 RR 不变。独立的 buffer pool 128→512MiB属于容量配置变化，须另列实际部署身份与前后证据，不计为本代码单项收益；后续正式容量仅据完整实测窗口判定。
