## 2. 固定领域规则

> 2026-10-24 规则变更：原“每用户每活动终身限购”改为“同时限购”。未支付取消/超时后可重新购买；已支付退款后仍占用资格、不可重买。数据库以 `UNIQUE(user_id, voucher_id, active_flag)` 兜底，详见下文。

| 项目 | 首版决策 |
| --- | --- |
| 购买单位 | 一单一张券，不接受客户端数量或金额 |
| 限购 | 每用户每活动同时最多一张有效订单（orderStatus 1/2/3）；未支付取消后可重新购买，已支付退款后不可重买 |
| 预约失败 | 只有 Redis 受理、确定 DB 无订单且落单明确失败时，可退预约库存并释放资格；结果未知时不释放 |
| 金额 | 以分为单位；`pay_value/payValue` 是购买价格，`actual_value/actualValue` 是抵扣面值，订单 `pay_amount` 快照购买价格，不使用前端价格 |
| 支付期限 | 默认落单后 15 分钟，可由配置调整；写入订单快照，配置变动不改变旧单期限 |
| 销售期 | `[begin_time, end_time)` 仅控制新预约；服务端时钟判断 |
| 核销期 | 独立的 `[redeem_begin_time, redeem_end_time)`；与销售期分别配置，要求核销结束时间晚于销售结束时间 |
| 支付截止 | `pay_deadline_at = min(DB 落单时间 + 配置期限, redeem_end_time)`；截止时刻开始拒绝支付并允许关单 |
| 退款 | 已支付、未核销且当前时间早于核销结束时间，OWNER/MANAGER 可执行整单模拟退款；不等待核销期开始 |
| 过期 | 已支付订单过期不自动改为退款，也不再核销或退款；需后续售后规则时另开范围 |
| 库存回补 | 取消、退款均只恢复一次 DB 库存和对应 Redis 库存；取消释放资格标记，退款保留资格标记 |
| 不可售库存 | 活动结束、下架后发生补偿，只恢复账面剩余量，不能重新变成可售活动 |
| 活动变更 | 发布请求确定后不修改库存、售价、门店和各时间；下架后不恢复 |

即使消息积压到核销期结束后才落单，也沿用快照截止时间，由关单任务立即关闭未支付单；不可把销售结束误当成拒绝处理已受理消息的理由。首版需把这种积压作为异常告警与故障验收场景，不能声称已受理必定成交。

DB 会话、Go 时间转换与 API 序列化统一使用 `Asia/Shanghai`；Redis 传输时间用 epoch 毫秒。写入时以 DB 当前时间执行支付/关单等边界判断，测试允许注入时钟，避免浏览器、Go进程和数据库分别决定是否过期。

## 3. 两类状态分开表达

### 3.1 异步处理状态

`state` 仍为 `PROCESSING / CREATED / FAILED`。`CREATED` 只表示 DB 订单存在，不表示仍未支付。

- DB 订单存在：返回 `state=CREATED`，并填 DB 当前 `orderStatus`；取消、核销、退款后也如此。
- DB 订单不存在且预约仍待处理：`PROCESSING`，`orderStatus=null`；不确定提交结果也保持处理中，并提示待核对。
- 只有已确认落单失败且持久化拒绝结果后，才返回 `FAILED`；未知结果不能包装成失败。
- 查询优先使用 DB；Redis 预约状态不得覆盖已存在订单的最终业务状态。

### 3.2 业务状态机

数据库继续使用 `tb_voucher_order.status`，DTO 继续使用 `orderStatus`：

| 数值 / 名称 | 允许动作与结果 |
| --- | --- |
| `1 UNPAID` | 本人模拟支付为 `2`；本人取消或到期关单为 `4` |
| `2 PAID` | 授权商家核销为 `3`；OWNER/MANAGER 在期限内模拟退款为 `6` |
| `3 REDEEMED` | 终态；禁止退款、取消或重复产生核销效果 |
| `4 CANCELLED` | 终态；禁止支付和核销，不恢复购买资格 |
| `6 REFUNDED` | 终态；禁止核销和支付，不恢复购买资格 |

`5 REFUNDING` 首版不启用，迁移发现旧状态 5 必须先人工确认，不能直接转换。重复提交同一已完成动作返回幂等结果；与当前状态冲突的其他动作返回明确的业务错误。只有首次成功转换产生审计、库存变化和 outbox 事件。

## 4. 身份与门店权限

每次服务端查询或变更都重新解析登录用户，检查商家及成员 `ACTIVE`。门店必须同时属于该商家；错误的 `tb_member_shop_scope` 记录不能跨越商家边界。

| 操作 | 普通用户 | OWNER / MANAGER | STAFF |
| --- | --- | --- | --- |
| 用户订单列表、支付、取消 | 仅本人 | 仅作为购买用户操作本人订单 | 仅作为购买用户操作本人订单 |
| 发布、查询本商家活动、下架 | 无 | 本商家门店 | 只读授权门店活动，不可发布/下架 |
| 商家订单查询 | 无 | 本商家门店 | 显式授权门店 |
| 核销 | 无 | 本商家门店 | 显式授权门店 |
| 模拟退款 | 无 | 本商家门店 | 无 |
| 审计查询 | 无 | 本商家门店 | 无 |

退款首版由商家执行；用户页展示退款状态和联系商家说明，不增加用户退款申请、审批表或审批状态。前端隐藏按钮只负责体验，直接调用 API 仍执行同样的权限校验。

`ShopAccessService` 应提供只读范围与具体操作权限，不能仅返回一个“有门店权限”的布尔值。查询必须在 SQL 中限定本人/授权门店，不先全表取回再过滤。用户查询其他人的订单统一返回不可见结果；商家越权操作返回 403，不回传核销 token 或订单隐私。

## 5. 最小数据迁移（计划中）

新增版本化迁移，例如 `infra/mysql/003-trade.sql`，由实现 agent 提交。下表是最低字段语义；可以调整 SQL 类型细节，但不得减少业务约束。

| 表 | 新增或调整 |
| --- | --- |
| `tb_seckill_voucher` | `total_stock` 初始总量；`publish_status` 为 `INITIALIZING/ACTIVE/OFFLINE`；`publish_version` 单调版本；独立核销起止时间；`publish_request_key` 和请求摘要用于发布重试；保留现有销售起止时间及剩余 `stock` |
| `tb_voucher_order` | `shop_id`、`pay_amount`、核销起止时间快照、`pay_deadline_at`、`cancel_time`、`cancel_reason`、`redeem_token VARCHAR(64)`、`version`、`active_flag` 生成列；保留既有支付/核销/退款时间 |
| `tb_audit_log` | 增加 `operator_type` 区分 USER/MERCHANT/SYSTEM；成功动作同事务写入；系统关单使用明确系统身份，不能伪造普通用户 |
| `tb_outbox` | `id` 自增主键、`event_id` 唯一事件标识、资源类型/ID/版本、事件类型、JSON 载荷、投递状态、尝试次数、下次重试时间、租约到期时间、最近错误、创建/完成时间 |

必要索引与约束：

- 用 `UNIQUE(user_id, voucher_id, active_flag)` 替代原 `UNIQUE(user_id, voucher_id)`：`active_flag` 为存储生成列，`status=4`（CANCELLED）时为 NULL，其余为 1。这样同一用户同一活动同时只有一笔有效订单，取消后可重购；退款（status=6）仍占用资格。`UNIQUE(redeem_token)`，未支付单允许 NULL。
- 订单增加 `(status, pay_deadline_at, id)`，以及 `(shop_id, create_time, id)`；本人列表使用既有用户时间索引并以 ID 作稳定次序。
- 发布请求键按商家唯一。若放在活动表，增加商家 ID 快照并设 `UNIQUE(merchant_id, publish_request_key)`，门店与商家归属由服务端校验；相同键不同摘要报冲突。
- outbox 使用唯一事件 ID，并以 `(aggregate_type, aggregate_id, aggregate_version, event_type)` 防止同一转换重复生成事件；增加 `(delivery_status, next_attempt_at, id)` 索引。
- 数据库剩余库存和初始库存均非负；订单快照字段不依赖后续读取活动当前价格。

当前订单表**没有 `shop_id`、核销码或支付截止时间**，不能直接运行包含这些列的 SQL。通过 `voucher_id → tb_voucher.shop_id` 回填旧订单；旧金额只能按现存演示活动回填，不能宣称恢复了不可得的历史价格。新字段先允许 NULL、回填验证、再设必要的 NOT NULL。

初始总库存根据已核实数据回填：剩余 DB 库存加状态为 1/2/3 的占用订单数；旧退款中记录和来源不明的库存差异必须先核对。旧活动先置 `INITIALIZING`，由显式准备过程恢复演示，不允许给全部活动默认开放 gate。

升级期间停止新预约，先核对或处理旧 Stream/pending 和待补偿事件。存在未落库预约时，不能把 DB 剩余库存直接覆盖进 Redis；旧活动恢复必须沿用已核对的预约差异，或完成清算后再准备。

Compose 初始化 SQL 只在空卷运行。已有卷使用明确的版本化迁移入口，不依赖容器重启，也不删除数据卷。迁移应维护版本/校验记录、检查列和索引是否已存在；MySQL DDL 可能隐式提交，中途失败要能从记录和结构检查恢复，不能盲目重复 `ALTER`。同时验证空库完整初始化和已有演示库升级。

## 6. 发布、下架与 Redis 准入 gate

`publish_status` 是新领域状态，不复用含义不明确的旧 `tb_voucher.status` 数字。展示、准入和后台统一按新字段判断。

### 6.1 发布协议

1. OWNER/MANAGER 提交白名单 DTO 和稳定的 `Idempotency-Key`；服务端确定商家与门店，校验价格/库存/时间并计算请求摘要。
2. DB 事务创建活动、库存和 `INITIALIZING` 状态，记录发布审计/事件。相同商家、请求键、摘要重复提交返回同一活动，不重复创建；不同摘要拒绝。
3. Redis 准备脚本写库存、时间、活动代次及默认关闭的 gate。准备只允许用于尚未开放过的 `INITIALIZING` 活动；重试不得覆盖已有库存。部分准备失败保持关闭。
4. 确认准备完成后，DB 事务将活动改为 `ACTIVE`、递增发布版本并写开放事件。只有确认 DB 已 ACTIVE 后才执行对应版本的开闸脚本。开闸失败由事件重试；此时可暂时显示准备中，不提前接受预约。
5. Lua 必须检查 gate 存在且为开放状态、活动代次一致、销售期、库存、限购记录；gate 缺失或关闭一律拒绝。不允许只凭有库存或 DB 时间校验就放行。

所有 gate 变更携带单调版本；脚本拒绝旧版本，等版本只允许相同动作。开闸必须基于已存在、同代次的完整准备信息，不能对 gate/代次丢失的 ACTIVE 活动自动重建并开放。禁止延迟到达的开放事件覆盖下架关闭。客户端在发布超时后使用同一请求键查询/重试，不重新生成活动。

### 6.2 下架协议与线性化边界

下架成功的边界是 Redis gate 已同步关闭；不能只改 DB 后等待异步事件慢慢关闸。

- 在串行化活动变更的 DB 行锁/短事务内，计算下一版本，同步用 Lua 关闭 gate，再将 DB 置 `OFFLINE`、写审计和关闭事件后提交。该 Redis 调用必须有明确短超时（建议可配置为 1 秒，并短于 DB 事务/锁超时），锁内禁止等待退避或无界重试；失败即尽快释放 DB 锁，由新的幂等请求继续处理。
- Redis 关闭失败，接口不报告下架成功；重试幂等。Redis 已关闭而 DB 提交失败时，保持关闭以保证安全，并将该活动标记为需完成下架；相同下架请求重试完成 DB 事务。不得把 Redis 自动修复回开放。
- 旧开放事件的版本较低，不能重新开闸。开放 relay 还必须读取 DB 当前发布状态与版本，不以旧 payload 单独决定开放。
- Lua 在关闸前受理的预约属于已受理，继续落单；关闸后新预约失败。消费者不能以当前 `OFFLINE` 或销售结束为由拒绝原先有效的受理消息。

首版的活动编辑操作只有上述首次发布和一次性下架，不增加恢复上架接口。初始化器不得在应用重启时对 ACTIVE 活动简单 SET 当前 DB 库存；那会遗漏未落库预约。

### 7.1 计划 DTO 示例

以下是 P1 的目标请求/响应，当前尚不能调用。已有接口保留原路径与兼容字段；列表统一使用 `data` 数组及 `total`，`current` 从 1 开始，`pageSize` 有服务端上限。商家列表可按授权门店、状态、订单 ID 筛选，SQL 始终先限制真实数据范围。

发布活动使用 `Idempotency-Key` 请求头（客户端为同一次发布保留同一个 UUID），请求体示例：

```json
{
  "shopId": "1",
  "title": "咖啡体验券",
  "payValue": "1900",
  "actualValue": "3000",
  "totalStock": 100,
  "beginTime": "2026-10-25T09:00:00+08:00",
  "endTime": "2026-10-25T18:00:00+08:00",
  "redeemBeginTime": "2026-10-25T09:00:00+08:00",
  "redeemEndTime": "2026-11-01T22:00:00+08:00"
}
```

金额、库存必须是合法正整数，购买价格不高于抵扣面值；标题长度、金额/库存上限、时间顺序与核销期限由服务端校验。拒绝负数、溢出、小数库存、无归属门店和额外可写身份字段。时间 API 带明确时区偏移，后端转换到业务时区，数据库与 JVM 时钟需保持同步。

发布响应至少包含 `id / publishStatus / ready`；DB 已 ACTIVE 而 Redis 未开闸时 `ready=false`，页面继续显示准备中。失败后使用原请求键或活动 ID 重试；相同键不同内容返回冲突。

订单详情保留旧字段，逐步增加以下业务字段。此例是已支付订单；只有本人合法查询才返回核销 token，公开报告示例不放真实 token：

```json
{
  "success": true,
  "data": {
    "id": "9223372036854775000",
    "state": "CREATED",
    "message": "订单已创建",
    "orderStatus": 2,
    "shopId": "1",
    "payAmount": "1900",
    "payDeadlineAt": "2026-10-25T09:15:00+08:00",
    "redeemBeginTime": "2026-10-25T09:00:00+08:00",
    "redeemEndTime": "2026-11-01T22:00:00+08:00"
  }
}
```

未落单时 `orderStatus=null`，不能伪造金额和期限；未支付不返回 token，终态不再展示可核销凭证。支付/取消/退款成功或同动作幂等重试返回当前业务详情，不将不同动作的状态冲突伪装为同动作成功。

抢购重试需要在 Lua 同一次执行中保留 `userId → 已受理 orderId` 映射，或等价的稳定受理索引；同一预约返回原 ID。返回原 ID 是幂等查询结果，不是新受理，不追加第二条下单消息，也不再次扣库存。压测与业务指标按唯一订单 ID 统计受理量，不能把所有 `success=true` 响应相加。已有 DB 订单始终可通过本人列表找回；未支付取消/超时后，在取消补偿完成并释放资格及原预约映射后可发起新的抢购，已支付退款后仍不可新建。确定落单失败时只清理由该失败预约拥有的映射，避免误删后续新预约。

核销 token 使用密码学安全随机数，至少 128 位随机熵，编码后存入 `VARCHAR(64)` 唯一列；碰撞在事务回滚后有限重试。页面支持粘贴，扫码可以后置，不使用低熵 8 位码。日志、审计、商家列表和错误响应不输出完整 token；核销接口仍应校验身份、限速和门店，不把持有 token 视为授权。

## 8. 事务边界、幂等与事件

### 8.1 落单与消息重投

- Go 显式事务统一使用 tx 完成 DB 条件扣库存、订单快照、创建审计与 `ORDER_CHANGED` outbox 事件；只有提交成功才认定已创建。提交失败/结果不确定走 pending/review，不能 ACK 或释放资格。
- 收到旧消息先按订单 ID 查 DB 并校验用户/活动。已存在则读取当前业务状态，不重设为 1、不再次扣库存。Redis 中 FAILED 也不能覆盖 DB 已存在的事实。
- 相同用户活动已有其他订单，属于确定的限购拒绝；释放本次多余预约但保留原订单购买资格。DB 扣库存为 0 属于明确业务拒绝。
- 明确拒绝先记录可重放的 `RESERVATION_REJECTED` 事件，再执行一次性退预约；确认无 DB 订单后方可清理该预约占位。Redis 状态过期不能成为猜测 DB 未提交的依据。
- DB 提交结果未知先查主库核对；无法确认继续重试/待核对，不能释放库存。达到重试上限不代表已失败。
- 已提交订单或持久化拒绝/待核对记录后才允许 ACK。死信应保留 sourceId、orderId、原因与时间；结果未知但 ACK 的消息必须另有 DB 可追踪记录，不依赖 24 小时预约 TTL 作为唯一证据。
- DB 不可用、无法提交 NEEDS_REVIEW 记录时，即使已经重试 5 次，也不得仅写 Redis 死信后 ACK；原消息继续保留 pending，退避重试并告警，待 DB 可用后确认结果或持久化待核对记录。重试次数是调度/告警阈值，不是丢弃消息的授权。

拒绝事件可用资源类型 `RESERVATION` 写入 outbox，不要求先有 DB 订单；结果未知时写 `ORDER_REVIEW_REQUIRED`，状态为 NEEDS_REVIEW，保留用户、活动、原消息和预约 ID，普通 relay 不把它当作库存回补指令。

### 8.2 支付、取消、核销与退款

可采用订单行锁后执行条件更新，或等价的条件更新实现；权限、当前状态、期限校验与变更处于同一 DB 事务。不得用前端先查询结果代替写入条件。

| 动作 | 变更条件与同事务效果 |
| --- | --- |
| 模拟支付 | 本人、`status=1` 且 DB 当前时间小于支付截止；改 2、写 pay_time、生成 token、审计、outbox |
| 主动取消/自动关单 | 本人取消，或 SYSTEM 且已到期；`status=1` 改 4、写原因/时间、DB 库存 +1、审计、outbox（释放资格标记） |
| 核销 | 授权门店、匹配 token、`status=2` 且核销期内；改 3、写 use_time、审计、outbox |
| 模拟退款 | OWNER/MANAGER、所属门店、`status=2` 且未到核销结束时间；改 6、写 refund_time、DB 库存 +1、审计、outbox（保留资格标记） |

订单版本在每次成功转换时递增；每次转换只创建一个唯一业务事件。状态变化成功而审计或 outbox 插入失败时，整笔事务回滚。审计操作人由登录上下文或可信系统任务上下文确定，不能从请求体接收。

取消或退款无需为了等待 Redis 而持有 DB 事务；用户端按 DB 结果展示业务成功，商家活动页可显示可售库存更新中，不向普通用户暴露事件队列或数据库细节。后续效果必须有可恢复的事件。模拟支付与核销不回补库存，商铺 `sold` 统计不作为库存正确性依据。

### 8.3 outbox relay

每个 `ORDER_CHANGED` 事件携带事件 ID、订单 ID/版本、活动与门店、目标状态、库存回补量（取消/退款为 1，其余为 0）、是否释放 Redis 资格标记（取消为 true，退款为 false）及必要追踪信息，不包含完整核销 token。

1. 短 DB 事务用 `FOR UPDATE SKIP LOCKED` 领取到期事件并记录租约；网络调用放在事务外。租约到期可被其他实例接管。
2. Redis 效果使用 Lua 按事件 ID 去重；先验证键类型、活动代次和库存键存在，再完成回补及去重记录。重复投递返回已处理；事件存在于 DB，不能因 Redis 超时就丢弃。
3. 库存键不存在时返回 `NEEDS_RECONCILIATION`，不执行 `INCR` 造出一个值为 1 的库存，不把该事件标为已成功。保留事件和差异告警，等待活动核对。
4. Redis 已成功而 relay 未写完成就退出，重试命中同一事件 ID，不重复回补。成功后标记 DONE；失败退避，超过阈值保留 NEEDS_REVIEW 记录而非删除。
5. 事件和去重标记保留期覆盖所有重放窗口；禁止去重记录过期后自动重放旧补偿。若 Redis 丢失代次/去重信息，则先关闭准入并核对，不能边恢复库存边重放旧事件。

Lua 同脚本只保证执行时不被其他命令插入，不保证运行错误回滚已执行的写入。所有脚本必须在第一次写入前校验参数数量、数值/范围及所有涉及键的类型；准入脚本尤其先检查 Stream、库存值、限购集合、受理映射、预约 Hash 和 gate，再扣库存并追加消息。补偿脚本同样先验证库存和去重键。可预检的参数/错类型异常必须零变更，验收需验证“库存、限购、预约、消息均未局部修改”；不可预检的运行故障不得假定自动回滚，应停止该活动准入并核对。

Lua 与 Stream 的执行边界在 Redis；业务事务与 outbox 的原子边界在 MySQL。二者不是同一个事务，不声称 exactly-once 或断电零丢单。首版继续按单 Redis 实例实现，不宣称 Lua 已适配 Redis Cluster。

## 9. 关单、故障恢复与核对

ZSet 只存订单 ID 和支付截止时间，用于快速发现到期单。任务执行仍按 DB 状态和时间条件更新；处理失败保留提醒并重试，成功后才移除。丢失、重复或未写入 ZSet 均不能影响最终关单。

DB 定时兜底查询 `status=1 AND pay_deadline_at<=DB当前时间`，按截止时间/ID 分批扫描，复用同一关单服务。多实例重复扫描也只有一次状态转换；无需先建设独立延迟队列产品。

| 失败位置 | 预期恢复行为 |
| --- | --- |
| Redis 已受理、消费者退出 | pending 在空闲阈值后接管；重投读取 DB 当前状态 |
| DB 落单成功、ACK/状态回写失败 | 旧消息重试不扣第二次库存，查询显示 DB 真实状态 |
| DB 取消/退款成功、Redis 未回补 | outbox 自动恢复，事件 ID 去重回补一次 |
| Redis 已回补、relay 尚未标 DONE | 租约到期重放，库存不再增加 |
| ZSet 提醒丢失 | DB 到期扫描发现并关闭 |
| 发布部分失败或客户端超时 | 关闭 gate，同一请求键/活动 ID 安全重试 |
| 旧开放事件晚于下架事件 | 版本检查拒绝，不重新开闸 |
| 库存/gate/代次缺失 | 拒绝新预约，输出差异并进入核对；不自动 SET DB 剩余量后开放 |

静止且已处理完所有预约/补偿的活动应满足：`初始总库存 = DB剩余库存 + 状态1/2/3订单数`，且 Redis 剩余量与 DB 剩余量一致；购买资格标记集合等于 orderStatus 1/2/3/6 的用户集合（4 在取消补偿完成后移除）。活动关闭后 Redis 键若已归档，应单独标记无在线库存，不能假装数值一致。

只有相关异常和事件清单已枚举完整、且已确认各记录是否占用库存时，才能使用瞬时差异公式：`Redis剩余量 = DB剩余量 - DB无订单且Redis仍扣占的未释放预约数 - DB已回补但Redis尚未执行的数量`。未释放预约同时包括待落单预约和“已明确失败但补偿尚未执行”的预约，不能只统计正常 PROCESSING。核对必须列出预约、已创建订单、明确失败、待确认和补偿事件；未知提交结果、Redis 数据缺失或脚本局部写入不能完整分类时，单列未知差异并停止给出库存正确的结论，不能硬套公式。

Redis 数据丢失或提交结果未知时，先停止相关活动准入，再结合 DB 订单、Stream/pending、拒绝/待核对记录和 outbox 清理差异。无法确认的预约不凭空释放，不宣称能自动恢复已被 Redis 丢失且无其他持久记录的全部已受理请求。保留 AOF everysec 的故障边界。

人工重放必须复用同一事件/订单 ID、同一权限和审计规则；不得通过删除订单、清空限购集合、直接 INCR 或直接改订单状态来“修复”。P2 可提供仅本地运维可用的命令工具；若做 HTTP 管理接口，另行定义管理员鉴权，不把全局重放权授给普通商家。

## 10. 实现交付时必须附带

- 实际迁移入口与执行说明，空库和已有库升级结果；不要求用户删卷。
- 新 API/DTO、前端订单状态与按钮的对应表；明确哪些仍计划中。
- 真实 MySQL/Redis 下的正常链路、跨门店/角色拒绝、支付关单竞争、退款核销竞争、重复消息和补偿故障恢复证据。
- 对账原始结果、事件状态和同一订单的成功审计记录；以 [验收清单](./acceptance.md) 为交付门槛。
