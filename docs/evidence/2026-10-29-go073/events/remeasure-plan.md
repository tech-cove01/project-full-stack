# GO-073 事件量化重测计划

首轮预热失败及环境快照见 [initial-report](initial-report.md)。此计划创建时尚未执行重测；具体结果、最终 SHA 和限制另行记录。

1. 等交易稳定负载及独立代码修复结束。核验 Git 完整 SHA/后端源码与构建元数据，从新的源码编译 API 与搜索 CLI；确认新端口 3411、6511、9121、9221、8123 可用。启动独立 `project-full-stack-go073-event2` 全新卷，显式迁移 003–012 并在 API 和消费者启动前离线重建索引，不手动建 Kafka topic、不修改 offset；使用 AI 关闭配置。记录宿主机已有服务和资源竞争。
2. 使用真实 HTTP 登录、10 个预热笔记与点赞，再按每秒一个笔记和一次点赞持续 180 秒，记录每笔请求开始/结束、异常与按约五个请求一次的 Elasticsearch 可见观察；结束后补尾部观察。记录实际开始、结束和请求总数，不能将预期速率代替实际速率。可见时间以请求开始到首次轮询命中为上界，包含轮询间隔及测量开销，不是精确索引提交时间。
3. 独立只读 Kafka CLI 20 秒间隔采样三组 committed/log end/lag，带每组调用时间与原始结果；它只覆盖部分稳定阶段，样本最大值不是全程峰值，CLI 消耗资源应在结果中披露。SQL 逐 event 记录 MySQL 同库 `create_time`、outbox `completed_at` 与 receipt `applied_at` 的微秒差；这不依赖跨主机时钟，但仅限数据库时间精度，receipt 不是搜索可见性。
4. 先等全部已发布事件各组 receipt、实际索引可查询及位点屏障；核对 Compose 标签后只停止本轮 Elasticsearch，真实发布及点赞 10 次，记录 Kafka 三组位点、持久停车数和事实。随后启动同一容器和原代次，只重放本轮停车坐标，记录启动、健康、精确重放和最终可查询的时间。按每个 event × 三组校验 APPLIED/IGNORED，逐笔核对点赞事实/计数和索引版本；lag=0 不能替代停车和索引确认。
5. 保存每轮新 JSON、原始 offset/事件及错误，验证不含身份凭据；停止本轮 API 与精确 Compose project 的四服务并保留卷，记录停止方式及实际退出码。只报告实际事件规模、时间、数据与未覆盖边界，不把历史单节点故障证据当成持续容量结论。
