# CAP-10-POOL-1：有界社区Relay工作池

S5→S6的活跃索引对照改善了扫描退化，但S6仍无法在800次实际点赞变更/秒下维持Outbox稳态。用户随后明确取消最多一项优化和旧执行次数/预算限制，要求同次云机继续修复并最终统一汇报。旧S5/S6失败、超时恢复和所有计量原件保持，不把不同阶段收益混算。

新增`GO_COMMUNITY_RELAY_WORKERS`，默认1、范围1—8。本次验证8个lane；每lane领取、同步RequireAll发布、租约栅栏完成仍逐条进行。各lane独立保存`lastEvent`，共享原数据库20连接池和并发安全Writer；统一取消并等待所有lane退出，只有原owner关闭Writer一次。不改变BatchSize、持久化、lease、retry、topic分区或活跃索引。

同key仍进入同分区，但并行领取和重试可能导致版本乱序；保持已有投影版本栅栏、幂等收据与ES版本机制，不能再声称版本必然按发布顺序到达。LIKE事件仍由三组明确IGNORE，不能将其说成三组物化写更新。

验收包括配置默认/边界、取消退出、独立空库64事件8路领取无重复且全部DONE、现有lease/retry/Kafka集成、相关普通测试/vet及精确源码CI。容量继续以同800/s比较，后续选定档位与同版本两轮180秒；原始业务正确性/时延/下游标准不变。工作池可能增加数据库连接竞争，最终收益与可持续档位只按实际负载报告，不按lane数推算。
