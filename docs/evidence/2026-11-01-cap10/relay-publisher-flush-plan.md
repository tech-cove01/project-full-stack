# CAP-10：缩短同步发布器的分区凑批等待

2026-11-03。状态见根[STATUS](../../../STATUS.md)，本票不增加云端压力窗口。

## 问题与改动

候选BatchPublisher每lane仅一个同步Writer、一次未决Publish。kafka-go按partition凑批，配置BatchSize=32时，一个已完整提交的32事件调用分到不同partition后，仍可能等待原10ms BatchTimeout；同lane在等待ACK期间不会再提交下一批。这个等待是新的批发布路径的组件开销，不能说它已被证明是旧S16的唯一瓶颈。

本票只将opt-in Writer的凑批等待10→1ms。RequireAll、Async=false、MaxAttempts1、5秒写超时、10秒调用ctx、字节预算、envelope、错误后真实Close/drain、整批保守未确认及SQL完成fence均保留。默认单条Worker不走此发布器，HTTP仍同步提交MySQL事实/计数/Outbox。

更短的凑批等待可能在调度暂停时拆出更多Produce调用，增加broker协议开销；不保证任意环境始终每partition一次请求。每个事件仍须收到实际ACK，失败保留原至少一次重放。回退只需恢复原10ms配置，不涉及表或数据迁移。

## 有限组件对照

使用同一程序、锁定的实际kafka-go Writer、立即返回的内存协议transport、32事件/2个可用partition；三个配对重复交替顺序，各版本每次12个计量样本，预热单列。不是实际Kafka、HTTP或PTS负载，不给出业务QPS。
