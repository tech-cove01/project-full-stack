# GO-073-CAP 容量与瓶颈补测计划

任务依据：[STATUS 顶部 GO-073-CAP](../../../STATUS.md)。起点为干净提交 `6faf9a93006969410fa05f710ce82706a8271bd7`。本计划在加压前固定方法和预算；旧 5 req/s 与函数级实测继续按原范围保留。本票新增测量器、观测及必要优化，每项单独审读与提交，实际构建 SHA/散列另记；本文件不宣称任何容量成绩。

## 固定环境和资源

- Windows 本机 i9-13900H（14 核/20 逻辑处理器），约 31.63 GiB RAM；Docker VM 20 CPU / 16,572,063,744 bytes，Docker Engine 29.3.1。API 与 k6 同机、数据库/Redis 在 Docker VM；CRM 等已有容器保持原状，必须记录共享资源和背景噪声。
- 专用交易项目 `project-full-stack-cap-trade`：MySQL 3450 / Redis 6550 / API 8250 / loopback 诊断 8350 / k6 控制 8260。专用读项目 `project-full-stack-cap-read`：3451 / 6551 / 8251 / 8351。新卷、合成夹具，无其它 API 消费本票 Stream/outbox；两个环境正式负载错峰，非当前实验依赖停止但保留卷。
- `compose.go.yaml` 加 [capacity override](../../../scripts/load/compose.capacity.yaml)：MySQL 4 CPU / 2 GiB，Redis 2 CPU / 512 MiB；原 InnoDB、事务、审计、AOF 等行为保留。API `GOMAXPROCS=4`、`GOMEMLIMIT=1GiB`（软限制），正常 MySQL 池 20 open/10 idle、Redis 池 10。实际镜像 digest、参数、数据与构建记录在环境证据中，不把限制外推为生产配置。
- AI、Kafka、ES 不参与交易/Feed 容量档，正常交易 worker 保留；不引入真实模型调用。社区高写入容量不由交易或 Feed RPS 推断，本次优先完成 STATUS 指定的交易和 HTTP 读链路。

## 预固定每档判据

同时记录目标到达率、实际迭代发起、实际 HTTP 请求、唯一受理、窗口内 SQL 成单与最终同批成单，VU 数和 RPS 分开。所有请求及成功请求延迟分别保存。

1. 发起率达成至少 99%，dropped=0；系统失败 / 全部请求 <1%；全部请求与成功请求均 P95≤200 ms、P99≤500 ms。库存足够时业务拒绝逐类列出，不能用售罄或重复填充成功吞吐。
2. 交易末段队列不能持续增长：使用每 2 秒采样的 lag、PEL 和 SQL 已提交数量；稳定阶段最后三分之一的 lag 净增长不得超过 2 秒目标到达量，且最后三分之一成单速率至少为该段实际受理速率的 98%（注明采样边界误差）。持续持有的最高档另检查完整末分钟，不依靠降载后清空掩盖持续积压。
3. 每档停止后排空并做精确订单/用户/活动匹配、重复有效订单、SQL/Redis 库存、accepted、review、拒绝/补偿和 Stream 对账；最高稳定档排空应在 15 秒内。正确性失败立即停止并保留现场，不继续升级。
4. 安全预算：未落单 lag>1000、队列最老未处理观测>15秒（可观测时）、连续窗口系统失败>5%，或资源采样触及主机内存88%、API RSS1.5GiB、k6 RSS2GiB、任一自有容器内存85%、主机CPU85%连续三个样本时，停止新请求并排空。连续三次进程/诊断/容器观测不完整也停止该档，记为不可测。采样只能提供观测值，不能保证抓到瞬时峰值。资源先触界时报告为共同部署/资源预算限制，不能称理论服务端上限。采样器仅发 stop-file 信号，监督器负责停止自己的生成器；采样器退出码0不代表该档达标。

## 小任务和执行顺序

- **CAP-01**：可扩展合法用户池/VU、低扰动流式落证、持久 SQL 聚合和 Redis 队列采样；以短探针核对预期/实际计数、逐 ID 去向、终止与恢复。外部采样脚本记录自身开销；进行同条件有/无观察短对照及短响应生成器探针。这里只验证测量方法，不出容量结论。
- **CAP-02**：单活动热点，每档用独立新活动、充足库存和不重复的用户-活动对，账号可跨不同活动复用。10→25→50→100 req/s，每档 45 秒探索；仍达标且有资源余量才继续200/400，首个受限档附近缩步。每档均排空/对账。最高达标档保持180秒并至少重复一次；边界在两档之间就报告区间，不追固定数字。
- **CAP-03**：真实 `GET /feed/notes`，固定6400篇合成笔记、32个作者/32个读者，每人关注一个作者，每页20项。hot=同一读者首页20计数键，multi=32读者均匀轮转640计数键；其余条件相同。25→50→100→200→400 req/s探索，按结果继续或缩步，最高档180秒重复。鉴权、SQL事实校验、点赞装配和缓存均走实际接口；数据库投影回退模式明确记录。SQL digest 与 Redis commandstats 的差值包含背景及观察开销，要区分计数回源与页面其它查询；两种key分布不能直接归因为缓存提升。
- **CAP-04**：首个受限档采集实际池等待、runtime/GC/goroutine、API/k6 CPU/RSS、容器资源、SQL digest/锁等待与队列。必要时在该独立环境显式开启标准 pprof，不额外部署观测平台；先给未经优化的基线和瓶颈证据，确有原因才做一个最小优化及直接相关回归。
- **CAP-05**：同资源、数据分布、负载与观测条件复测，交最高稳定/首个受限档、生成器余量、排空、对账、失败与限制。自测不提升为独立验收；推送完整 SHA 供核验者在另一环境复跑。之后更新 README 与私有简历素材，旧报告原字节保留。

## 方法来源

本机工具链沿用已安装版本，不因查文档升级。k6 [开环模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)和 [constant-arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/)用于把发起调度与响应时间分离；VU 用尽仍会丢弃迭代，须与实际发出率和负载器资源一起判断。[Go pprof](https://pkg.go.dev/net/http/pprof)仅在显式 loopback 诊断监听器使用。原始结果不是静态规格推导，必须由本票实际运行产生。
