## 统一业务口径

> 2026-10-24 规则变更：取消后可重购（A 方案），退款后不可重购；下文与对账不变式已按此更新。

### 两种状态分别判断

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `state` | `PROCESSING` | 已受理，尚未确认建单；重试耗尽且结果未决时仍可保持此状态 |
| `state` | `CREATED` | 订单已在数据库创建；后续取消或退款也不改成 `FAILED` |
| `state` | `FAILED` | 确定无法建单，且处理结果可解释 |
| `orderStatus` | `1 / 2 / 3 / 4 / 6` | 未支付 / 已支付 / 已核销 / 已取消 / 已退款 |

数据库订单表的物理列可以仍叫 `status`；报告、接口和页面讨论业务状态时统一称 `orderStatus`。`PROCESSING` 期间 `orderStatus` 可以为空，不能把抢购返回订单 ID 当成数据库已建单。所有订单 ID 在 JSON 和前端状态中均保留字符串。

- 一用户一活动同时只允许一笔有效订单（orderStatus 1/2/3）。未支付取消/超时关闭后释放 Redis 资格标记，可重新抢购；已支付退款后保留资格标记，不可重买。重复请求可返回原受理 ID 或明确拒绝，不能再次扣库存；数据库使用 `active_flag` 生成列唯一约束兜底。确定建单失败且从未产生订单的预约释放，另按失败原因处理，不能与已创建订单取消混淆。
- 默认支付期限为创建订单后 15 分钟，配置项可调，且不晚于核销截止，最终以订单期限快照为准。验收可缩短到 10–30 秒并记录配置；应在支付请求中检查数据库截止时间，不能靠定时任务是否及时执行决定能否支付。
- 核销只允许已支付订单，退款只允许已支付且未核销订单。取消只允许未支付订单。重复操作不产生第二次状态迁移或库存变更；幂等重试可返回原结果，不要求所有重试都报错。
- 核销凭证使用至少 128 位安全随机 token；不采用 8 位可枚举码。校验唯一性、门店授权、状态与使用次数；日志和报告对 token 脱敏。
- 取消、退款的数据库库存回补、状态变更、业务审计及 outbox 事件在同一事务提交。Redis 回补由可重试、幂等 relay 执行，不能将两次写入描述为跨 Redis/MySQL 原子提交。
- Redis 回补前必须确认库存键存在、类型正确；缺键时保留事件及告警/待对账状态，不执行 `INCR` 创建虚假库存。补偿事件必须携带是否释放资格：取消释放，退款保留。
- 延迟 ZSet 是提示，不是订单事实源。ZSet 丢失、服务停机或调度重复时，由数据库到期订单扫描兜底。

## 固定测试数据与隔离

实现 agent 提供可重复执行的测试数据准备和只读核验脚本，注明写入范围。使用独立测试库/Redis 实例或明确隔离的测试环境，不复用个人开发中的活动 `1001`。各场景使用新的活动 ID，防止历史限购标记污染结果。

| 数据 | 固定约定 |
| --- | --- |
| 商家 | 商家 A、B；A 有门店 A1、A2，B 有门店 B1 |
| 权限账号 | A 店主；仅获 A1 授权的 A 店员；B 店主；无商家身份的普通用户；另验证商家或成员停用后的原 Token |
| 普通用户池 | 至少 200 个有效登录账号，Token 不写入 Git 或报告；账号准备与登录不计入抢购吞吐 |
| 多账号争抢 | 新活动，初始数据库/Redis 库存均为 `100`，200 个不同用户各提交一次 |
| 单账号重试 | 另一新活动，初始库存 `100`，同一用户同时提交 `20` 次 |
| 故障与业务场景 | 每个场景独立新活动，初始库存 `100`；记录实际成功受理的订单 ID |

## P1：交易与 B 端闭环

新增交易迁移后，同时验证新库初始化及从基线已有库升级，检查字段回填、约束、旧订单/预约处理和迁移重复执行策略；不能只证明空卷初始化成功。

| 编号 | 操作 | 通过条件及独立证据 |
| --- | --- | --- |
| P1-1 | A 店主发布 A1 活动；重复提交发布；模拟发布投递重试；下架后投递旧开放事件 | 数据库活动、库存及开放状态正确；发布重试不重置已售库存；旧 `ACTIVE` 事件不能越过较新 `CLOSED` 状态重新开闸；记录事件版本及库存前后值 |
| P1-2 | 不同用户分别完成“抢购→支付→核销”“抢购→主动取消”“抢购→支付→退款” | `orderStatus` 分别到 `3 / 4 / 6`，`state` 均为 `CREATED`；金额、时间及操作人正确；取消/退款最终各回补一次 DB/Redis 库存；取消后资格标记移除，退款后保留，核验 `SISMEMBER` |
| P1-3 | 取消后原用户再次抢同一活动；退款后原用户再次抢；新用户购买已回补库存 | 取消后原用户可创建新订单；退款后原用户不得新建或扣库存；新用户可购买；核对 active 订单唯一约束及 Redis `SISMEMBER`，不只看前端按钮 |
| P1-4 | 缩短支付期限；并发支付与关单；移除延迟提示或停机越过截止时间后恢复扫描 | 到期后拒绝支付；最终只有支付或取消一方有效；ZSet 缺失仍会关单；记录期限、请求时间、状态和库存变更次数 |
| P1-5 | 对同一凭证并发核销 20 次；另对已支付订单并发退款与核销；重发取消/退款请求 | 每个订单最多一次有效终态迁移；退款与核销互斥；不重复回补；核验数据库状态、审计、outbox 与 Redis，而非只数 HTTP 成功响应 |
| P1-6 | 店员跨 A1/A2 或调用仅管理角色可用的退款/发布接口；A 店主跨 B1；普通用户调用商家接口；停用商家/成员后持原 Token 操作；篡改 `shopId`、订单 ID、商家 ID | 服务端按当前角色、有效状态及归属拒绝；列表、详情、核销、退款及发布均覆盖。核查业务状态、库存、审计/outbox 无非法变更；安全拒绝日志可正常存在 |
| P1-7 | 模拟状态/库存更新后审计或 outbox 写入失败；同一补偿事件重复投递；补偿时库存键缺失 | 前者整体回滚；重投只回补一次；缺键不生成库存并保留可恢复事件。核销 token 唯一且至少 128 位，猜测或重放凭证不绕过权限与状态检查 |

## P2：可靠性/并发证据

| 编号 | 操作 | 通过条件及独立证据 |
| --- | --- | --- |
| P2-1 | 单账号 20 个并发请求；多账号 200 人各争抢一次库存 100；分别重复运行独立活动 | 同账号最多一笔有效订单，重复请求可返回旧 ID 或拒绝；多账号最多 100 笔；无负库存；各结果分类计数。无故障且期限未到时，最终建单数等于按唯一 `orderId` 去重的新受理单数 |
| P2-2 | 分别命中“消费后、事务提交前”与“事务提交后、ACK 前”终止消费者，再用新实例恢复 | 故障前证明具体订单/消息确在目标窗口，恢复后有领取、处理与 ACK 证据；已提交订单重投不再次扣库存；未提交事务不留半笔数据。随机杀进程但未证明命中窗口不算通过 |
| P2-3 | MySQL 短暂不可用后恢复；另一轮超过重试上限，再对账及重放 | 不确定结果保留 `PROCESSING`/待核对，不直接放库存；只有已有订单或 DB 持久化拒绝/复核记录才可 ACK，DB 不可用无法持久化时不得 ACK，仅 Redis 死信不够；恢复后去重受理 ID 均有归宿；旧建单消息重放不重复建单/补偿，已取消单保持 `orderStatus=4`、`state=CREATED` |
| P2-4 | Redis 正常重启与异常终止分别实验；恢复后对照受理日志及 DB | 记录真实命令、持久化配置、消息/预约/订单前后差异；区分正常恢复与灾难数据丢失边界，发现差异保留证据并说明恢复办法；不凭一次重启宣称零丢失 |
| P2-5 | 按已配置的用户与操作维度限流策略重复请求；正常多用户对照；如额外启用 IP 限流则单列验证 | 超限返回 429，未创建额外订单/事件或扣减库存；正常请求仍按业务规则处理；账号池、共享 IP 和阈值写入报告，避免测试程序全被 IP 限流后误报高吞吐 |
| P2-6 | 执行下述分层负载；有余力再对双实例缓存失效做断线实验 | 报告含原始结果及数据不变式；广播只能缩短旧值窗口，订阅端断线仍需 TTL/其他恢复机制，不能宣传强一致 |
| P2-7 | 在隔离环境将 Stream 或其他 Lua 依赖键设置为错误类型后抢购 | 所有可能失败的键类型校验在写入前完成；请求明确失败，库存、购买标记、预约及消息无部分写入；修复键类型后可正常受理。不能假定 Lua 运行错误会自动回滚 |

当前基线的消费者领取门槛为 60 秒，恢复扫描约每 30 秒一次。执行时按实际提交的配置给出恢复超时与实测耗时；不要沿用单笔冒烟 20 秒超时，也不要无限等待直到“总会通过”。

故障证据至少包含故障触发前后的订单 ID、Stream 消息 ID、消费者名、事务/ACK 时间线、只读数据库与 Redis 结果。可增加仅测试环境启用的受控故障点，但验收要观察真实 MySQL/Redis 副作用，不能由 Mock 返回值证明恢复。

### 对账不变式

所有受理数、建单数、吞吐及下述等式按唯一 `orderId` 去重；HTTP 成功次数另报。重复请求返回旧 ID 不算新受理，窗口内找回先前受理 ID 也不计入本窗口新受理单数。

每个活动记录初始库存 `S0=100`。在停写、消息与补偿事件追平、所有未决项归类后的稳定窗口，定义 `C` 为 `orderStatus IN (1,2,3)` 的订单数，则应满足：

```text
数据库剩余库存 = S0 - C
Redis 剩余库存 = 数据库剩余库存
同一 user_id + voucher_id 的 active 订单数 <= 1（active = orderStatus 1/2/3）
购买资格标记：orderStatus 1/2/3/6 保留；4 在取消补偿完成后移除
每个唯一受理 orderId = 已创建 / 确定失败 / 明确列出的未决，三者之一
```

运行中 Redis 预扣与 DB 落库、DB 回补与 Redis 投递之间存在合法差异，不能直接要求每毫秒相等。对账报告须逐项列出未落库预约、已提交但未回补事件、死信及不确定事务结果，防止同一订单重复计入差异。存在未决记录时标记“未收敛/待处理”，不能宣称全部自动恢复。

`pending=0` 只表明没有待 ACK 的已投递消息；未读积压、死信、人工复核以及未完成 outbox 仍可能存在。验收须一起查看消费组积压、pending、死信、预约和补偿事件，而非只看一个指标。

示例只读核验（替换 `@accept_voucher_id`；以下 `SET` 仅设置 SQL 会话变量）：

```sql
SET @accept_voucher_id = 910001;

SELECT voucher_id, stock FROM tb_seckill_voucher
WHERE voucher_id = @accept_voucher_id;

SELECT status AS orderStatus, COUNT(*) AS orders
FROM tb_voucher_order WHERE voucher_id = @accept_voucher_id
GROUP BY status;

SELECT user_id, voucher_id, COUNT(*) AS orders
FROM tb_voucher_order WHERE voucher_id = @accept_voucher_id
GROUP BY user_id, voucher_id HAVING COUNT(*) > 1;

SELECT 100 - COUNT(*) AS expected_remaining
FROM tb_voucher_order
WHERE voucher_id = @accept_voucher_id AND status IN (1, 2, 3);
```

```text
GET seckill:stock:<voucherId>
SISMEMBER seckill:order:<voucherId> <userId>
HGETALL order:reservation:<orderId>
XINFO GROUPS stream.orders
XPENDING stream.orders g1
XRANGE stream.orders.dead - + COUNT 100
```

实现 agent 另提供与最终表结构对应的审计/outbox 核验查询、死信分页导出及未决订单清单。不要把前 100 条样本当成完整对账。

### 性能负载与指标口径

本项目使用 k6，复用并扩展现有脚本。先验证账户、活动、业务检查及对账，再增加负载。

| 负载层 | 操作 | 目的与记录 |
| --- | --- | --- |
| 小规模烟测 | 例如 20 VU、1 分钟；热点查询与抢购分开跑 | 验证脚本、真实后端、业务断言和结果导出；这是示例参数，不是性能承诺 |
| 逐档校准 | 例如以 20/50/100 目标 RPS 逐档试验，再据机器容量调整 | 记录实际达到的 RPS、排队/丢弃迭代、资源和错误；闭环线程/VU 模型同时记录并发数、等待时间，不能把 VU 写成 RPS |
| 业务并发 | 200 用户争抢 100 库存；另做足量库存的下单吞吐测试 | 稀缺库存场景证明正确性；容量测量避免绝大多数请求已售罄、只测到快速拒绝路径 |
| 稳定观察 | 校准后选择可持续档位，预热后持续足够时间观察消费与资源趋势 | 例如数分钟并明确窗口；不凭 30 秒无异常推断长期稳定或生产容量 |

必须分开报告：HTTP 成功次数、去重的新受理吞吐、最终建单吞吐、受理响应 P95/P99、受理至最终结果 P95/P99、店铺查询 P95/P99，以及售罄、重复/旧 ID 找回、活动无效、429、鉴权错误、5xx/超时、业务 `success=false`、未决订单。

HTTP 200 也要解析业务结果。429、售罄和重复请求在对应场景可为预期结果，但不得静默从全部统计中移除；系统异常率与业务拒绝率分别定义并给出分母。失败请求也保留耗时，成功路径耗时单独列出。任何“错误率 < 1%”“P95 < 100ms”等只可作为可调整实验目标，不作为预先达成的结论。

负载机与服务同机时注明资源竞争。账号准备、登录、冷/热缓存、预热窗口、数据规模、支付期限及是否启用限流必须写清。报告保留 CPU/内存、数据库连接、Redis/Stream 积压等足够定位瓶颈的观测，Grafana 截图不能替代原始结果。

Redis 当前基线使用 AOF `appendfsync everysec`，灾难情况下存在最近约 1 秒写入丢失风险，单实例也不提供故障切换保证。正常重启实验不代表断电或磁盘损坏实验；详见 [Redis 持久化文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。

## P3：可选扩展

ES 使用独立 profile，主业务不依赖其启动。至少验证：中文搜索/过滤结果、数据库与 outbox 同事务、重复及乱序投递不覆盖较新文档、写入至“可被搜索”的延迟、停写并追平后的同条件 DB/索引对账，以及 ES 不可用时真实降级行为。异步索引不能承诺实时聚合与数据库完全一致。

深分页、复杂相关性和全套聚合可以后置。若实现 `search_after`，需稳定唯一排序，并明确索引变化时是否使用 PIT。IK 插件与 ES 版本匹配。扩展功能单独提供证据，不以新增技术名词替代 P0–P2 的通过结果。

## CI 分层

| 层级 | 触发与检查 | 能证明什么 |
| --- | --- | --- |
| 构建与单元测试 | 每次 PR：现有后端 verify、前端类型检查/构建；按仓库规范检查格式 | 编译、局部逻辑、Mock 调用路径；不证明真实依赖行为 |
| 真实依赖集成 | P0 起补充：独立 MySQL/Redis、SQL 初始化/迁移、Lua/事务/HTTP 冒烟；P1 补关键业务竞争与权限 | 本次提交在固定依赖下的真实副作用、约束与事务行为 |
| 浏览器联调 | P1：连接真实后端，覆盖一条用户到商家流程、刷新恢复及权限拒绝 | 页面与 API 的实际配合；Mock 测试另列 |
| 并发与故障实验 | P2：手动/定向运行于隔离环境，绑定提交并上传证据 | 指定环境、数据和故障窗口下的结果；不能外推无限容量与零丢失 |

CI 输出按层分开标注。单元 CI 绿灯不能让未执行的可靠性、压测或 ES 项目变为通过。集成测试可以使用容器服务或 Testcontainers，但必须是真实依赖，不以 H2/Mock 替代。

## 实现 agent 的结果交付格式

每阶段提交一份 `docs/evidence/<日期>-<短SHA>/<阶段>/report.md`，保存可追溯的原始结果；Token、验证码、核销 token 和环境密码脱敏，账号池放被忽略的本地文件。不要只交一段“全部通过”。

```text
提交：完整 SHA；分支；是否存在未提交改动
环境：OS/CPU/内存；JDK/Node/MySQL/Redis/工具版本；单/多实例；端口
数据：测试库/活动ID；初始库存；用户数；活动时间；支付期限；限流配置
复现：准备命令 → 执行命令 → 只读核验命令 → 限定范围的清理步骤

编号 | PASS / FAIL / 未执行 | 期望 | 实际 | 原始证据路径

对账：HTTP成功次数；去重新受理数；已创建/确定失败/未决；各orderStatus数量；DB/Redis库存
恢复：故障命中窗口；消息ID；时间线；恢复耗时；死信/补偿事件归宿
性能：负载模型；目标与实际RPS；统计窗口；分类错误；P95/P99；资源
限制：未验证场景、未决事项、已知风险；本阶段是否满足进入下一阶段门槛
```

原始证据至少包括测试报告、请求结果摘要及可追溯 ID、压测原始输出、SQL/Redis 核验快照和必要日志。独立复核者应能从干净检出按命令重现，并用只读查询确认业务结果，而不必相信实现测试的断言或手工截图。
