## 3. 栈与兼容原则

Java 21 目标 / Spring Boot 3.5.16 / MyBatis-Plus / MySQL 8.4 / Redis 7.4 / Caffeine / Vue 3 + TypeScript + Element Plus / k6 沿用。新增 `spring-kafka` 由现有 Boot 依赖管理，锁定并验证对应客户端和 broker 版本，不为追新版本升级整个应用。

Kafka 用 Docker 单节点 KRaft 开发 profile，不额外维护旧虚拟机。官方提供 Docker 启动方式，具体镜像和客户端兼容性由实现批次锁定、记录；单节点不代表生产高可用。见 [Kafka 官方快速开始](https://kafka.apache.org/quickstart/)。

交易创建仍走 Redis Stream；活动/订单补偿仍走原 outbox。新增社区 outbox 独立表，防止两个 worker 抢同一事件或误将订单事件标记完成。不要借本任务重写交易消息链路。

AI 保留当前手写 OpenAI-compatible Provider、小规模内存精确检索和服务端规则路由。LangChain4j、Spring AI、模型 Function Calling 都不是本轮前置要求；未实际使用就不写进技术栈。SSE 阶段通知与模型逐 token 流式输出分别描述。

### H1：最小社区与数据契约

复用 `tb_blog` 的公开笔记内容、作者与门店关联；新增发布状态、发布时间和内容版本。复用 `tb_follow` 的唯一关系，改为保留 inactive 状态与单调版本，不用删除行丢掉旧事件判断依据。新增 `tb_blog_like`：`(blog_id,user_id)` 唯一，active、version；不在每次点赞中更新同一热点笔记的 DB 总计数行。新增独立 `tb_community_outbox` 和内部稠密 slot 映射。迁移放 `infra/mysql/migrations/` 下一可用版本，同时更新新库初始化/迁移文档。

增加每用户持久 Feed 版本，在关注变更的同一 DB 事务递增；下一次个性化请求核对当前版本，不依赖尚未消费的 Kafka 事件判断是否已取关。笔记查询索引至少覆盖 `(user_id,status,published_at,id)`，关系表覆盖正向/反向有效关系查询；通过 EXPLAIN 和实际请求核查，不为所有字段堆索引。旧 `tb_blog.liked` 仅是历史投影，迁移时处理旧点赞数据，不能与新事实表并列为两个事实源。

以下为计划 API；路径可随现有响应风格调整，但语义与验收不删减：

| API | 语义 |
| --- | --- |
| `POST /notes` | 白名单标题/纯文本/门店字段；作者取当前登录身份；服务端生成 ID/版本/发布时间 |
| `GET /notes/{id}` | 公开已发布内容，返回公开计数和当前用户 liked；不暴露作者私有字段 |
| `GET /notes/feed?tab=following&cursor=...&size=...` | 固定发布时间倒序；游标包含 `(publishedAt,id)`；首次关注页展示当前关注作者的最近公开笔记 |
| `PUT /notes/{id}/like` | `{liked: true/false, requestId}` 设置期望状态，不做 toggle；DB 提交后返回当前状态/版本，计数允许短暂投影延迟 |
| `PUT /authors/{id}/follow` | `{followed: true/false, requestId}`；禁止关注自己/不存在作者；身份取服务端 |
| `GET /authors/{id}/relationship` | 当前身份关注状态与公开统计；事实状态可从 DB 校验 |

同关系并发用行锁/唯一约束与事务重试串行裁决；重复期望状态不新增业务效果。关系变更与 outbox INSERT 在同一 DB 事务提交；事件含稳定 eventId、schemaVersion、聚合键、单调关系版本、目标状态、时间。Kafka key 按关系聚合，不能假设同 key 分区自动修复生产者重试引起的旧事件。

前端新增笔记列表/详情、简易发布表单、点赞按钮、作者关注按钮、关注动态 tab；使用现有请求/会话组件。ID 保持字符串；提交禁重、失败回滚、状态查询、空态和分页结束可见。旧 `/blog` 等不安全写入口不能直接去掉 403 就开放；实体绑定、旧点赞/关注服务必须被替换或仍保持关闭。

Kafka relay 使用短事务认领/带租约恢复 → 事务外发送 → broker 确认后标记完成。发送结果不确定就用相同 eventId 重发。broker 不可用时 outbox 可见积压、恢复可投递；不能提交 DB 后丢事件，也不能把“DB 已提交”显示成“全部缓存已更新”。

### H2：点赞状态与紧凑计数

事实源是 DB 关系，Redis 是可重建投影。首版以点赞一个指标做深，收藏/阅读计数不为凑数量加入。

1. 为用户和笔记分配内部稠密 slot，持久化映射。位图按用户 slot 分段，例如每段 65536 bit；不能将外部 64 位 ID 直接当 SETBIT offset。笔记计数按笔记 slot 分段使用 `BITFIELD u32`。
2. Lua 校验键类型、参数、范围、当前版本和计数上下界；新事件根据旧位与目标状态计算差值，原子更新位图、计数及已应用关系版本。旧/重复事件无效果；不能直接对每条消息盲目 `+1/-1`。多消费者实例处理同关系仍正确。
3. 选用明确溢出行为并拒绝不合法结果，不能默默 wrap。`BITFIELD` 是在 Redis String 上进行位域整数操作，底层使用 SDS 不等于另造存储引擎；命令语义见 [Redis BITFIELD](https://redis.io/docs/latest/commands/bitfield/)。
4. missing key、版本/计数矛盾、不可判定的部分执行进入 NOT_READY/待重建；读取回退 DB 或返回明确重建状态，不把缺失计数当 0。对于已知类型/范围错误要在写前阻断；脚本异常不具备数据库式回滚，不能宣称任意故障下零副作用。
5. 首版允许受控短暂停社区写入：关闭写入口、等待在途 DB 事务及 outbox/消费排空 → DB 一致快照 → 构建新 generation → 比较关系总数、BITCOUNT 与计数 → 切换 generation → 恢复写。重启中断可继续或丢弃未发布 generation；不要求在线无停顿重建。版本元数据保留策略必须覆盖可能重放的历史，不能短 TTL 去重后永久保留可重放事件。
6. 比较相同语义的 Hash 基线与紧凑方案。汇总 slot 映射、位图、计数、关系版本、generation 等全部 Redis 键的 `MEMORY USAGE`，同时列稠密/稀疏用户分布；不要只算 4 字节计数。若总成本更高，如实解释，保留配置回退，不强写“节省 60%”。

写接口包含 DB 关系持久化，性能不能与仅执行 Redis Lua 的数字混称。计数与当前用户 liked 可以有短暂不同步，前端按提交返回的本人状态展示，投影追平后刷新总数。

### H3：Feed 分层缓存与热点保护

| 层 | 缓存内容 | 隔离与失效 |
| --- | --- | --- |
| L1 Caffeine | 当前用户一页 ID/公开内容组合，不含本人 liked | key 含用户、tab、游标、size、Feed 版本；容量上限、短 TTL |
| L2 Redis 页面 | 有序笔记 ID、下一游标与 Feed 版本 | 个性化 key；取关版本变化后旧页失效；不能只按页码共享 |
| L3 Redis 片段 | 公开笔记内容/作者公开摘要/内容版本 | 跨页面共享；本人 liked、角色、私有订单均不进入共享片段 |

查询用 DB 基线或可重建的 Feed 索引生成稳定顺序；批量拼接片段避免 N+1，再装配本人点赞状态。分页同毫秒跨三页不能重复或漏项；不要照搬旧 timestamp+offset 实现。关注变动后前端重置游标，后端返回新 Feed 版本；下一次请求通过当前 DB 关系/版本拒用旧关系缓存，不能等缓存自然过期才隐藏已取关内容。

hotkey 使用有容量上限的滑动窗口计数与进入/退出阈值，先作用于共享笔记片段。热点 TTL 有最大值，冷却后回到普通策略；内容修改/下线仍能失效。普通 TTL 加受限随机抖动，不能延长订单/活动价格等实时事实的缓存。

同 key miss 用 Caffeine 原子 `get`/异步加载合并，失败释放并允许重试；现有店铺实现可借鉴。[Caffeine 官方加载说明](https://github.com/ben-manes/caffeine/wiki/Population)支持这种本地合并方式。首版只保证每进程同 key 一个加载，不宣称跨实例全局 single-flight；两个实例需记录各自加载次数。L1 通知失效可配短 TTL 兜底，但不能把 Pub/Sub 当可靠事务总线。

补指标：各层命中、DB 加载次数、合并等待、热点进入/退出、key 数量与容量、P95/P99。热缓存高吞吐与冷 miss 防风暴分别实验，不能只测重复查同一页。

### H4：关注链路与多投影恢复

至少交付两类有业务用途的消费者投影，不为凑截图的“五个下游”制造空消费者：

- 关注索引：正向关注、反向粉丝、公开计数。关系版本比较 + 目标状态更新，重复/逆序取关不重复扣数；多键失败可发现并重建。
- Feed：笔记发布分发、关注变化导致索引/缓存版本更新。首版小规模 fan-out，有批次/游标和重试；首次关注展示作者近期内容，取关后不再展示该作者。DB 查询是正确性回退路径，不能把 Redis ZSet 当唯一历史。

不同 consumer group 分别确认自己的效果后提交 offset。处理失败有退避、有限重试、持久死信/待处理状态与受控重放；不能静默吞异常。失败的投影不阻塞无关投影，但页面要表达未追平或走事实查询；本地低负载以 5 秒内追平为验收目标，积压期间另测恢复耗时，不承诺硬实时。

证据覆盖：关系 DB commit 后进程退出；broker 断开；发送成功但尚未标记完成；consumer 效果写入后尚未提交 offset；同关系快速反向操作；一个消费者持续失败；清空本任务投影后重建。端到端为至少一次投递 + 幂等应用，不宣称跨 MySQL/Kafka/Redis exactly-once。

### H5：AI 收口与证据

AI 保留“公开规则 RAG + 本人实时订单/活动只读查询 + B 端知识维护”，已有页面继续使用。H0 修边界后补以下最小项：

- [ ] 按 FAQ/标题/段落做有上限的逻辑分块，保留来源位置和内容 hash；同文档版本幂等索引，停用/替换后只有一个生效版本。已发布内容可形成新草稿，或明确使用“新文档替换 + 停用旧文档”的最小路径。
- [ ] 索引加载失败/缺块有明确状态与恢复方式，不能默默用旧知识；请求只检索当前授权门店与已发布版本。
- [ ] 固定问题逐题核对事实、引用是否支撑答案、工具数据是否符合当时快照；来源标题命中率不能标答案准确率。Stub 的故障覆盖与真实模型正常质量分开。
- [ ] 展示真实阶段与取消/失败；没有模型原生 token 流就不宣传逐 token 输出；不强加 AI 摘要、预取或新 Agent。预取仅在后续证明同身份/门店/知识版本下有收益再做，避免额外费用和旧答案复活。

H5 同时完成交易持续负载、社区 API/内存/缓存对照、前后端演示及文档。每个实现批次应已交付对应小测试，不把全部验收堆到最后。

### H6：可选 Canal 同栈适配

如果时间允许，再以 Canal 订阅已提交的社区 outbox INSERT，将 CDC envelope 转成与轮询相同的领域事件后发 Kafka。不能把所有业务表变更当领域事件直接消费；poller 与 CDC 对同一流二选一，切换重复仍由消费者幂等防护。

实现前实际验证 MySQL 8.4 的 binlog 配置、ROW/FULL、复制权限、认证方式与所选 Canal 版本；锁定镜像，记录位点/GTID 持久化与 binlog 清理后的恢复流程。[Canal 官方 Kafka QuickStart](https://github.com/alibaba/canal/wiki/Canal-Kafka-RocketMQ-QuickStart)说明了投递模式，但其中旧版本示例不能证明兼容当前 MySQL 8.4，不照搬关闭防火墙等环境操作。

必须验证回滚事务不发事件、断连追赶、重启位点、旧消息重放和适配器切换；未通过时回到已验证 poller，不牵连交易启动。H6 未做不阻塞本轮冻结，但 README/简历必须写真实投递方式。
