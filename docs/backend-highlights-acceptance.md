# 后端亮点增补验收

日期：2026-10-26。配套 [增补方案](backend-highlights-plan.md)。以下均为待验收；构建成功、已有源码、截图数字都不是完成依据。

## 1. 测试准备与证据

使用项目独立 MySQL/Redis/Kafka 测试实例或明确隔离的测试环境；停服务、清投影、删 key 和负载实验只能作用于该环境。保留已有业务数据，不删除数据库卷。

正确性最小数据：3 名作者、2 名读者、至少 50 条笔记；一批笔记故意使用相同发布时间，跨至少三页；补一个大 64 位外部用户 ID 验证 slot。另准备 OWNER-A / STAFF-B 混合角色。负载规模单独记录，可从 100 作者、1000 用户、10000 笔记开始，测量前说明关系密度和分布。

证据目录建议 `docs/evidence/<日期>-<短SHA>/community/`，含 README、场景矩阵、脚本、脱敏响应、SQL/Redis/Kafka 快照、原始 k6 JSON/摘要与时间线。记录应用/脚本完整 SHA、未提交 diff、真实版本/镜像 digest、机器资源、配置、实际执行命令和数据准备/限定清理方式。Token、密钥和完整核销凭据不得入 Git。

状态仅用 PASS / FAIL / 未执行 / 不适用。可选 H6 未执行应单列，不能把未执行当通过。独立核验者能在不引用忽略目录或私有账号池的条件下复现。

## 3. 压测与优化对照

选择 k6 复用现有 JS 脚本体系，无需为本轮另装 JMeter。工具选择不代表结果有效，固定数据、请求模型和指标分类才是验收依据。负载脚本、账号准备和只读对账入口一同交付。

社区每档建议先 30—60 秒预热，再持续 3—5 分钟；从本机能承受的 20/50/100 RPS 起测，逐级加压，记录到达率、实际完成率、VU、迭代和 dropped iterations。并发正确性使用同步起跑的独立场景，不把账号数当同时在途请求数。

| 实验 | 同条件对照 | 必须记录 |
| --- | --- | --- |
| 点赞 | Hash/紧凑 Redis 布局；完整写 API 与仅 Lua 微基准分开 | 成功/限频/系统错误、P50/P95/P99、DB/Redis 操作和 CPU/内存；投影追平后事实对账；全量辅助键内存 |
| Feed | DB 基线 → 缓存分层 → 热点保护；相同页面分布 | 各层命中、DB 查询次数、热点分布、失效期间加载峰值、延迟、错误；冷/热结果分开 |
| 关注 | 同步投影基线与 DB+outbox 异步投影 | DB 事务/API 耗时与事件最终投影耗时分别计量；积压与恢复结果，不只报告写接口变快 |
| 原抢券 | 持续多账号负载及单账号重复场景 | 成功受理/售罄/限购/429/系统错误各自计数与延迟；受理至最终建单延迟；初末库存/资格/订单与未决数量 |

容量实验以观察拐点和守住正确性为目标；不要求达到他人截图的 QPS。延迟从客户端端到端采集，成功延迟不能混入快速售罄/拒绝；不能用 0.24 秒短突发外推出持续吞吐。连接拒绝、超时和失败轮次全部保留，定位后才能解释原因。

AI 评测单独运行，不混入交易/社区压测，不对外部模型做高并发压力实验。先用 Stub 覆盖异常与预算，再用小批真实调用验证质量；不为了取得漂亮数字重复刷题。

## 4. 最终交接与冻结

交付一段真实演示：商家发布活动 → 用户浏览/抢券/支付 → 店员核销 → 店主审计；用户发布探店笔记 → 另一账号关注/点赞/看动态；助手回答规则带出处并查询本人订单；B 端停用知识后旧规则不再返回。

README 介绍产品与实际能力，文档报告记录细节。简历亮点只能使用核验后的技术和实测数字；允许描述单实例、最终一致和短暂停写重建这些真实限制。H0—H5 通过后冻结功能；H6、ES、额外 AI 功能不阻塞进入面试准备。
