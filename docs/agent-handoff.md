### 单个任务交付可验证的行为

H0—H5 是阶段，不要把一整个阶段作为一次不可中断的大任务。每批从已有任务中选择一个能独立验收的功能或缺陷，覆盖必要的数据、API、页面和测试层；后端缺陷不强行新增页面。无需为拆任务先重构全仓。

当前批次的任务状态统一维护在 `docs/README.md` 第 3 节；阶段计划说明范围和顺序，验收文档定义通过条件，报告保存证据。README 其他进度表只摘要这些状态，不另建 `.scratch` tickets、`tasks.md` 或第二套勾选表。需要更多任务时在该节按以下字段增加，历史已完成项可以收成报告链接。

```text
任务 ID / 名称：
依赖：写明确实阻塞的任务 ID；没有依赖写“无”
交付行为：一个完成后能演示或验证的结果
范围：本任务包含什么；已确定的可选扩展不混入本任务
验收：关联现有验收 ID，并列出本任务最关键的成功/失败行为
验证边界：接口/页面/事件，以及需要核对的持久业务不变式
验证结果：实际命令、PASS/FAIL/未执行、原始证据路径
版本：开始 SHA、交付 SHA；未提交时附暂存/工作区/新文件清单
状态：待做 / 进行中 / 自测通过待核验 / 已验收 / 受阻（写具体原因）
```

例如“同用户重复设置点赞仍只计一次”应交付设置期望状态的 API、关系唯一性/版本、必要的页面反馈及重复请求验证；它依赖笔记/身份基础和所采用的事件投影基础。后续“乱序消费仍收敛”“投影重建”可独立拆票，不把它们藏在一个“完成点赞系统”勾选里。示例是拆分方法，不表示社区已经实现。

### 关键行为先复现，再实现

库存、消息幂等/乱序、状态竞争、权限和 AI 生命周期缺陷，先用能命中窗口的失败场景确认，再修到通过。预期值来自业务契约或独立算例，不能复制实现里的判断来计算“正确答案”；HTTP 200、无异常、Stub 返回文本都不足以单独证明完成。

优先经 API、页面、消息消费等公开边界验证。库存/订单/补偿属于持久正确性契约，继续保留受控 SQL/Redis 对账和故障时间线，不因套用 TDD 原文而删掉这些证据；Mock、真实依赖和真实模型结果分别报告。页面格式化、文案及文档改动不强制新增测试。

开发期间运行与当前行为有关的小范围验证；每批完成后运行适用的完整检查。已经通过且未受新改动影响的重型压测/故障演练不反复跑。每次只推进一个小循环，避免先写一大批猜想测试、再一次性实现整个阶段。

### 审查覆盖需求与代码两方面

实现者自测后提交给核验者；复杂批次可以由两个只读审查者分别执行：

1. **需求符合度**：对照当前任务和验收，检查漏做、行为错误、扩大范围及虚报完成；给出实现/证据/缺失的对应关系。
2. **正确性与代码质量**：检查事务、状态、并发、权限、资源生命周期、迁移和项目约定；格式工具已覆盖的内容不重复人工挑错。长函数/命名等维护建议与影响业务的缺陷分开，不因偏好要求大重构。

两方面分别给结论，并标明实际执行和仅代码推断的边界。独立核验通过后，任务才从“自测通过待核验”转“已验收”；只覆盖限频不能把整个 AI 生命周期勾完，构建通过不能代替真实故障恢复。已通过部分保留，不重新开发。

审查先记录基线、HEAD 和工作区状态，规范路径明确传入本任务引用的 `docs/` 文件。如果未来使用 OpenSpec，显式传入对应 `openspec/changes/<change>/`，不依赖自动发现。至少覆盖：

```text
git rev-parse HEAD
git status --short
git diff <明确的基线> HEAD     # 本批已提交修改
git diff --cached             # 暂存区
git diff                      # 未暂存修改
git ls-files --others --exclude-standard  # 逐个读取相关新文件
```

有其他 agent 正在改文件时，注明审查版本；发生变化后补差量核验，不用旧结果替代新版本。审查不覆盖、清理或提交他人工作区；提交、推送及外部操作仍依当前会话授权处理。

参考原文：[to-tickets](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md)、[TDD](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)、[code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md)。本节保留当前项目的一份任务状态，未照搬其跟踪器、测试边界和审批约定。

## 文档优先级与协作

领域规则以 [transaction-design.md](transaction-design.md) 为准；阶段范围以 [implementation-plan.md](implementation-plan.md) 为准；是否完成以 [acceptance.md](acceptance.md) 和实际证据为准。若与新代码冲突，先检查差异、记录原因并同步规范，不能悄悄删减验收。

AI 领域补充以 [ai-design.md](ai-design.md) 及 [ai-acceptance.md](ai-acceptance.md) 为准；AI 知识种子跟随最新交易契约，尤其是取消后可重买、退款后不可重买的规则。

设计/核验 agent 负责规范、审查与独立复核，实现 agent 负责应用、迁移、脚本和初次自验。阶段完成时附以下清单，避免审查只依赖口头结论：

| 交付项 | 要求 |
| --- | --- |
| 版本 | 完整 SHA；有未提交改动时给出 diff 和状态，避免混合版本结果 |
| 环境 | Windows、JDK、Node、MySQL、Redis、k6 实际版本与机器资源 |
| 复现 | 初始化/迁移、启动、验证、只读对账及非破坏停止命令 |
| 场景 | 关联任务 ID 和验收 ID，分别记录期望、实际、证据 |
| 原始材料 | 测试报告、脱敏响应、k6 输出、SQL/Redis 快照、故障时间线、真实页面演示 |
| 限制 | 未验证项、未决订单、失败窗口、负载瓶颈、暂未实现内容 |

敏感 Token、验证码、完整核销 token 不进入公开报告；仅保留脱敏关联 ID。全部高负载测试使用独立测试活动与账号，数据准备和清理范围明确。
