## 1. 本次确定的交付范围

用户明确要保留主要后端亮点，做成完整项目；不因着急砍掉社区、Kafka、Feed。减少额外复杂度：Canal、自定义 SDS/BITFIELD 压缩计数、复杂自研热点算法、ES、微服务集群不作为完成前置。

最终产品：本地生活交易 + 商家运营 + 探店社区 + 业务 AI。一个后端和一个前端贯通以下三条真实流程：

1. 商家发布活动 → 用户抢券/支付 → 店员核销 → 店主审计；异常含取消、超时、退款与恢复。
2. 用户发探店笔记 → 他人关注/点赞 → 关注动态；缓存、事件投影及故障恢复有测量依据。
3. 用户问规则/查本人订单 → 助手给依据和实时结果；商家维护公开 FAQ，停用后旧知识失效。

### 四条亮点的目标写法

以下是开发与验收完成后的文案目标，**不是当前完成声明**；最终每条控制为约两到三行，以实际一页排版为准，数字只采用核验结果。

1. **高并发交易与幂等**：面向活动集中抢购，使用 Redis Lua 原子校验库存与资格，结合 Stream 异步建单、MySQL 条件扣减及有效订单唯一约束处理重复请求；通过多账号争抢、状态竞争与故障恢复验证库存和订单一致性。
2. **多级缓存与热点保护**：针对关注 Feed 读取，构建 Caffeine 本地页、Redis 页面与公开片段缓存；结合短窗口热点识别、TTL 抖动和同 key 加载合并，控制冷缓存回源并隔离用户状态，以持续负载对比 DB 访问量及 P95。
3. **可靠事件与最终一致性**：关注/取关与 outbox 在同一 MySQL 事务提交，经 Kafka 更新关系索引、计数及 Feed；使用关系版本、幂等消费、退避重试与持久待处理记录应对重复/乱序和消费者故障，核验恢复后的投影一致性。
4. **业务 RAG 与权限边界**：将公开平台/门店 FAQ 分块检索并展示出处，实时订单按当前身份只读查询；结合知识版本失效校验、隔离会话、原子消息去重和请求预算，覆盖资料停用与重复请求，避免旧规则重放和跨用户查询。

项目介绍用一句话说明 Vue 3/TS 用户端与商家工作台、OWNER/MANAGER/STAFF 门店范围及完整交易流程，不另凑一条“使用 Vue 写页面”。实习 3—4 条、本项目 4 条、Agent 项目 3—4 条作为排版起点；不照搬截图长段，按内容质量压缩。

### ES 的位置

当前没有 ES 依赖、服务或索引实现，只有 MySQL 店名 LIKE 查询及分类/GEO 旧接口，不能把 ES 写成已用技术栈。当前范围先补搜索/分类/分页即可；需要笔记多字段全文检索、相关性权重等明确需求时，再作为可独立关闭的扩展。能力示例见 [Elastic multi-match 文档](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query)。
