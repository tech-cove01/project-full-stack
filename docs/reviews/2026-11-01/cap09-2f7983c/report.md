## 已证实的修复与仍缺的观测

[SetLike](../../../../backend/internal/social/like.go)同步经过 Redis 鉴权、SQL 事务（笔记/关系锁、事实和计数更新、Outbox）、提交后 Redis 失效、SQL 回查与 Redis Mark；后台 relay 与三组 IGNORED 收据还共享数据库资源。这些步骤有实际成本，但本次正式组没有给每一步计时。

特别是当前 trace 只从 Feed 入口启动：[诊断预测](../../../evidence/2026-11-01-cap09/like-diagnostic-1-prediction.json)已明确 Like 没有 trace，诊断原件的 `tail.requests/shared_tasks` 也为 0。旧数据缺少逐请求时延序列和相应数据库/依赖等待图，无法从已有工件补算出“哪一段用了 200ms”。单笔记热点锁也不是直接解释：正式已核实 229 个用户分别修改 229 篇独占笔记，各一次，相关关系在稳定段前都已存在。

已有改动的价值可以如实讲：

- `9d8d9f6`：已确认事务提交后，用脱离 caller cancellation、独立 2 秒预算的同步上下文完成失效/回查/Mark。旧日志确有 SQL 已提交、Redis 仍旧的失败，新日志含提交前取消、提交后取消和旧版本围栏三项通过。这是实际一致性修复，不是异步受理或吞吐提升证明。
- `5e561b8`：串行 relay 每次只发送一条，设置 BatchSize=1 去掉等待 10ms 凑批的成本，保留发送确认与租约/重试规则。缺完整有效的优化前主场景基线，因此没有稳定 TPS 提升比例。
- `e6bfc77`：复用 Feed 的不可变 IANA Location，采样证明原分配热点消失；不同采样窗口不用于计算精确每请求或 RSS 收益，与点赞此次失败分开。

旧 observer 的收据查询约 2233→12.8ms 改善属于采集工具；该查询已在正式组前修复，不能当作业务提速，也不能拿旧采集失败解释新正式组失败。

## 还差什么才能收尾

若目标是功能和可靠性亮点，现有代码、故障修复及最终对账已经有材料。若目标是“稳定点赞吞吐”，最小缺口是：

1. **只针对点赞的一次有效分段观察。** 在原同步链路分开记录鉴权、事务总耗时/提交、失效、回查、Mark；只给慢段补对应依赖或数据库等待信息。复用现有有界观测，不重跑 Feed 或全阶梯。
2. **依据慢段做一个有证据的选择。** 若主要是代码或 SQL 往返，就做单项修复与必要回归；若确有宿主/依赖调度或 I/O 干扰，再做同代码的固定环境对照。不先盲扩池或假设换机器就解决。
3. **取得完整持有结果。** 预先固定预热、数据、目标速率及正式窗口，再按同版本完成 180 秒两轮、真实 mutation/事实/事件和下游核对。若调整早期百分位中止策略，作为新协议记录，保留最终 200/500ms 延迟标准与资源/正确性护栏；旧组继续保留失败。

以上是最小缺口建议，不是本轮已经执行或自动重开名额。按用户要求先交现有证据结论。

## 是否需要云机

**当前建议先不采购或部署云机。** 现有材料没有证明笔记本资源耗尽；最缺的是点赞阶段耗时。搬到云上会同时改变操作系统、网络、磁盘与资源竞争，新的数字也不能单独解释当前代码哪个步骤慢。

如果后续定位明确需要隔离宿主影响，优先利用已有可用 Linux 环境或一次固定资源对照；代码与业务语义保持，先测新环境基线，负载器资源另记。现有执行器还包含 Windows 供电/进程检查，上云需要适配这些采集和运行步骤，不是只改 API 地址。云测试作为新环境结果单列，Feed 仍不重复跑。
