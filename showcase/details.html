设计详解 / 从业务到实现

让每一次操作，
都有明确的结果。

一次消费连接用户、商家与社区。系统围绕这条业务链路组织模块，用事务保存事实，用异步任务衔接后续处理，用权限和版本约束每一次读取与变更。

01 / 一次完整消费

从活动发布，到到店履约。

用户端与商家工作台共享订单状态，取消、超时和退款也属于这条流程。

  1. 01 / 商家经营发布活动与优惠

    商家依据当前门店权限管理活动，设置库存与活动窗口；用户通过商铺分类、详情和公开优惠发现活动。

  2. 02 / 用户抢券受理请求，异步成单

    Lua 检查活动窗口、库存与用户资格，保存稳定受理映射并写入 Stream。后台事务创建订单，前端查询受理结果。

  3. 03 / 支付与关闭推进订单状态

    模拟支付进入待核销状态；用户取消或订单超时后关闭，补偿链路恢复对应预占，重复请求遵守幂等边界。

  4. 04 / 到店与售后核销、退款与审计

    有权限的门店成员处理核销和退款，事务内重查授权与订单状态；结果与操作审计一起落库。

  5. 05 / 社区发现分享体验，关注动态

    用户发布探店笔记、关注作者并点赞；关注 Feed 和公开笔记搜索帮助下一位用户发现商铺。

支付与退款为模拟资金流程。业务 AI 可辅助查询规则和订单，交易变更仍通过业务接口执行。

02 / 系统架构

三条链路，各自承担清晰职责。

后端采用 Go 模块化单体。订单使用 Redis Stream，社区使用 Outbox 与 Kafka；MySQL 保存最终业务事实。

交易：先受理，再形成可查询的持久结果

前端区分受理与成单，后台处理重复投递、未知结果与补偿。

社区：事实先提交，查询投影随后更新

点赞状态、计数与社区 Outbox 同事务提交；查询缓存和搜索索引围绕权威事实构建。

03 / 核心设计

把可靠性落实到每个边界。

重点关注重复请求、权限变化、旧数据回流和异步处理失败。

01

异步交易一致性与故障恢复

抢券重试与异步处理相遇时，需要回答：请求有没有受理，订单是否落库，重复消息会不会再次扣库存？

Redis Lua原子预占并保存稳定受理ID，Stream异步成单；MySQL事务与唯一约束保存最终事实，结果或待核对任务持久化后才确认消息。补偿检查预占归属，避免旧任务释放新订单的库存。

流程与取舍

受理成功只代表进入处理链路，不等于订单已落库。结果未知时先保留待核对记录，明确核对后恢复；取消后的补偿也需核对原订单和预占，重买产生的新归属不能被旧补偿覆盖。

02

Feed 分层缓存与并发回源控制

同一篇探店笔记被多人浏览时，正文可以复用，个人点赞和当前可见性却必须按本次身份与事实装配。

公共正文按笔记ID与发布版本进入进程内缓存和Redis两级缓存；缺失内容批量加载，相同缺失批次共享有界回源，单个请求取消不终止其他等待者。版本和失效代次约束旧加载回流。

流程与取舍

合并范围是同一进程内相同缺失批次，并非跨实例全局去重。缓存不存完整个人卡片；旧回源完成时仍需检查当前版本和可见性，不能把隐藏内容重新公开。

03

可靠事件与 ES 搜索一致性

笔记已经保存，搜索索引可能仍未更新；重复、乱序和索引故障不能让旧内容覆盖新版本或暴露已隐藏笔记。

笔记事实与Outbox同事务保存，经Kafka独立消费组更新ES；事件收据去重、业务版本约束乱序。搜索候选返回前回MySQL复核，失败事件持久停车，由人工明确重放。

流程与取舍

索引恢复可用并不等于失败事件已经处理。保留原事件坐标与停车状态，手动重放后记录效果与收据；隐藏后即使旧索引仍命中，也要按当前事实过滤。

04

高并发点赞链路优化

点赞接口成功，后续事件仍可能积压；容量需要同时检查成功写入、数据一致性与下游稳态。

合并事务SQL、有界发布与消费批处理减少数据库往返和提交开销，保留事务、租约与版本检查。点赞事实和计数同步写入MySQL，Kafka下游不承担异步落点赞计数。

流程与取舍

16核32GB单机，两轮各180秒内网正式验证均达到3000+成功QPS，P95均不超过62ms、P99均不超过102ms，并通过事实和下游校验。互动场景只解释机制；真实成绩保留H3/H4原始报告、独立PTS与1996组关系等条件。

补充

逐门店权限与并发履约

OWNER / MANAGER / STAFF 的操作范围由当前成员关系和目标门店共同决定。核销与退款在业务事务内重查并锁定授权，而非只相信登录时的角色信息。

  • 同一用户在不同门店的角色独立解析，接口按目标资源校验范围。
  • 订单状态、业务版本与操作审计一起提交，处理重复及并发状态变化。
  • 成员停用或权限调整后，后续敏感操作重新检查当前授权。
工作台如何与用户订单保持一致？

两端读取同一套交易事实。商家操作受门店范围和订单状态双重约束；前端负责呈现可用动作，服务端事务负责最终授权与状态判断。

04 / 技术实现

模块分工明确，源码顺着业务读。

交易、商家、社区、搜索和 AI 分模块组织，HTTP 路由、连接池与后台任务统一组装。

用户端与商家工作台

Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus；表单与列表承接交易、社区和经营操作。

API 与后台任务

Go、Gin、GORM、go-redis/v9；按模块组织处理器与业务服务，随进程生命周期管理消费与关闭。

数据、缓存与事件

MySQL 8.4 保存事实；Redis 7.4 负责 Lua、Stream 和缓存；Kafka 承接社区事件及独立消费组。

搜索与业务 AI

Elasticsearch、CJK 分词与游标分页；兼容 Chat / Embedding、Qwen、只读工具与应用层 SSE。
