## 叙事与视觉顺序

页面素材按“业务能做什么 → 完整链路怎样保证正确 → 明确环境下能承受多少 → 慢在哪里及实际改进”组织。首屏优先放一张真实业务界面和少量有证据的结论卡，图表旁保留场景、窗口和通过范围；详细环境、失败档与原件放入可展开的证据区。

采用统一中性色背景、蓝色数据、绿色通过、琥珀色受限、灰色未执行，并同时写明状态，不仅靠颜色。数字、单位、时间轴及图例保持一致。美观来自版式、留白、可读标注及真实对照；不通过删去失败、缩短分母、截断纵轴或修改截图中的数值提升观感。图表导出后能独立阅读，不依赖动效。

## 性能与正确性采集清单

仅在已有证据或本批剩余授权窗口自然产生数据时采集；本清单不新增压力轮、诊断窗或优化项。

| 素材ID / 图形 | 要回答的问题 | 必须保留的数据与展示方式 |
| --- | --- | --- |
| `feed-cap09-holds` / 两轮小表或并列点图 | 历史完整Feed的重复稳定结果是什么 | 原生窗口、9000与9001请求、各轮P95/P99/max、unknown/drop/内容校验、资源与下游结论；写明开发机、requests/s、非生产上限。不平均两轮P95/P99；100/s早停单列，不能画成完整45秒成绩 |
| `like-linux-search` / 档位表加吞吐—时延图 | Linux真实点赞的实测范围是多少 | 每个实际预约S窗的source/bin、速率、完整时长、已核mutation/s与HTTP PUT/s、计划/发起/完成/分类分母、P95/P99/max、unknown/no-op/drop、通过/性能受限/环境无效/正确性停止。只绘实际档位；未测率不补点。L/U仅来自同一最终源码的有效边界 |
| `like-linux-holds` / 两轮并列卡片 | 选定R是否完成两轮180秒 | 候选确认与H1/H2分别列出，标原生完整性和全链路判定。首轮失败时第二轮标“未执行”，不填0，不把短窗或单轮通过写成重复稳定 |
| `like-stage-breakdown` / 阶段面板与一条慢迹时间线 | 已测慢段的证据落在哪个边界 | 鉴权前总耗时、auth、service、transaction_total、commit_call、postcommit Invalidate / LikeState / Mark；native前后计数、总时长、均值、最大值、errors、active/oldest及有界慢迹。事务与SQL/Redis子段重叠，用嵌套时间线或并列面板，不堆成100%耗时饼图 |
| `like-single-change` / 同率A/B配对图 | 唯一改动是否带来可复核改善 | 若实际完成优化及同条件对照，列前后源码、唯一变量、同率同窗、相同诊断开关/夹具初态、全样本与mutation分位、吞吐、资源和正确性。无优化或无公平对照则不生成收益图，不以Linux对Windows、关诊断对开诊断计算“提升” |
| `like-queues` / 三行对齐时间序列 | 响应达标时下游是否持续积压 | Outbox未完成、三组缺失收据、三组Kafka lag共七条队列；标native起止、采样间隙、全窗及末段增长、同期事件分母、PARKED、首次恢复基线的真实SQL/Kafka完成时间。保留结束后60秒边界，最终排空不替代稳态 |
| `like-facts` / 对账表 | 高吞吐对应多少真实效果 | 主窗版本迁移、唯一LIKE_CHANGED事件、各笔记公开计数与active事实、Redis成员/版本，三组IGNORED收据分列；warm HTTP / 合成setup SQL / 主窗HTTP单列。IGNORED不称有效投影更新，幂等no-op不算mutation |
| `like-resources` / 同时间轴资源面板 | 是目标组件还是发压器/环境受限 | 宿主、API、k6+Node、自有容器CPU/内存；配额、cgroup版本、同窗节流增量、SQL/Redis池与可用锁/查询观测。累计历史节流不当本窗瓶颈；不可用项目标缺失，不补0；容器CPU标明按核数还是配额归一化 |

Like主窗以原生scenario开始和计划结束为横轴基准。warm/setup可在旁边单列耗时，不接入主窗吞吐分母；失败与中断样本保留unknown及覆盖范围。短窗末15秒、正式末60秒与全窗统计分别标识，5秒离散采样不称连续瞬时证明。

阶段图仅使用当前工具确实记录的指标：聚合count/total/max不能还原阶段P95/P99；count/total/errors可作已声明端点区间的差量，阶段max则是Recorder生命周期累计最大值，不能afterMax−beforeMax，也不能把afterMax当原生窗内max，只能标原端点累计值或选择性慢迹所见值。最多32条、每条256段、100ms阈值的慢迹不能代表总体时延分布。现有native summary保留avg/med/P95/P99/max，延迟采用P95/P99并列柱或两轮表，不伪造逐请求散点、直方图、CDF、箱线或请求级时延时序。资源/队列趋势只用既有5秒timeline；不为图增加全量采样、逐请求日志或native输出开销。SQL事务/Commit和Redis调用包络不能改名为纯锁等待、纯池等待或纯服务端执行时间。

历史Feed的时区缓存分配观察若用于附录，必须沿用[既有分配对照](../2026-11-01-cap09/feed-allocation-comparison.md)的限制：采样窗口不同、HTTP数差1、profile覆盖预热和背景工作；“未采到zone链”不等于绝对0，不把约17.28%的采样总量变化当确定单请求分配、尾延迟或吞吐收益。它不能代替Linux Like的单项对照。

## 导出文件与来源规范

后续素材统一放在本批证据目录下的 `showcase-assets/`；本次只写计划，不创建素材目录或伪占位结果。命名为 `<scenario>-<asset-id>-<revision8>.<ext>`，历史Feed使用 `feed-cap09-windows` 前缀，Linux Like使用 `like-cap10-linux` 前缀。

- 每张数据图交付PNG、SVG和JSON三件套。PNG以1600×900或按图内容确定的明确尺寸导出，文字在缩至800像素宽后仍可读；SVG保留文字、图例与矢量线条；JSON保存实际绘图数值、单位、状态、缺失原因和来源。可另附CSV供复算，但不替代JSON。
- 业务截图交付原始PNG、裁切PNG（若需要）和JSON；不把截图装成数据图，不伪造SVG版本。PNG可后续派生网页缩略图，原件保留。
- 制图使用标准绘图库生成可独立下载的静态工件；不依赖终端截图、AI绘制数据图或远端在线制图服务。记录制图脚本/工具版本及导出文件SHA256，同一JSON生成PNG/SVG。
- JSON逐图绑定完整应用sourceSHA、binarySHA256、前端SHA（界面图）、工具hash、环境manifest/hash、机器别名与实际CPU/RAM/磁盘/OS、部署拓扑、目标组件配额、夹具hash/规模、stage与native起止UTC、完整/中断、预热/setup政策、诊断/profile开关、各分母及实际延迟覆盖。字段不适用写null并解释，不将未执行写为0。
- 原件来源逐项使用仓库相对路径与SHA256；公开caption可显示短SHA，完整SHA保留JSON与证据链接。公开包只取已脱敏原件/必要统计，不复制private env、token、Cookie、SSH信息、私有简历或实习资料。只收录本项目材料。

## 采集完成的交接条件

- [ ] Linux是否执行、L/U/R及唯一优化的实际状态与STATUS一致；未完成项不在公开页面生成数字卡。
- [ ] 历史Feed、本机预检和Linux Like环境分组明确，失败、unknown、未执行及覆盖限制可见。
- [ ] 每图三件套（截图两类PNG加JSON）可离线打开，数值逐项回到原件，分母与单位一致，缺失不补0。
- [ ] 业务截图源于实际现有界面，文字清晰、角色和演示状态可解释，原图/裁切关系可追溯。
- [ ] 独立审读确认结论与证据相符、无私有资料混入；后续静态页的建站、浏览器视觉核验与发布另按当时任务执行。
