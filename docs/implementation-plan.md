# 技术选型与改造方案

## 目标与交付顺序

围绕本地生活活动交易，交付一个能够运行、演示、测试和解释设计取舍的全栈项目。先完成主链路，再增加运营玩法；每个阶段保留可复现的验证方式。

第一版的业务边界是：用户登录、商铺浏览、限量活动抢购、异步订单查询、商家角色和授权门店。接下来补活动发布与核销，使用户和商家围绕同一笔订单协作。

## 已定技术栈

| 部分 | 选择 | 原因 |
| --- | --- | --- |
| 架构 | 模块化单体；一个 API 服务 | 便于本地启动、事务管理和排查问题；后续按实际瓶颈拆分 |
| Java | Java 21；Spring Boot 3.5.x | 统一现代运行环境与 Jakarta API，兼容当前依赖 |
| 持久层 | MyBatis-Plus、MySQL 8.4 | 复用已有业务模型，同时明确事务和索引约束 |
| 会话 | Redis 保存随机 Token | 登录态撤销、TTL 刷新和开发联调简单；不同时维护多套 Token 方案 |
| 异步订单 | Redis Stream | 复用现有 Lua/Stream 链路，减少独立中间件；显式处理 pending、重试与死信 |
| 缓存 | Redis + 容量和 TTL 受限的 Caffeine | 复用高级示例中的本地缓存思路；用实验决定哪些查询值得进入 L1 |
| 前端 | Vue 3、TypeScript、Vite、Router、Pinia、Element Plus | 一个工程同时组织用户区和商家工作台，复用类型、请求与会话逻辑 |
| 本地运行 | Docker Compose | 固定数据库、Redis、演示数据与持久化配置 |
| 验证 | JUnit/Mockito、H2、HTTP 冒烟、k6、GitHub Actions | 单元与数据权限测试、真实服务联调、负载实验分别验证不同问题 |

第一阶段沿用 Redis Stream，不另行接入 Kafka/RabbitMQ。若后续以独立消息中间件做对照实验，再比较投递、补偿和运维成本。分库分表与服务拆分以测量结果为依据。

## 当前代码如何复用

- 实战业务主干已迁入 `backend/`，保留商铺、用户、优惠券、内容互动、GEO 和签到等逻辑；Java 包名统一为 `com.fullstack.platform`。
- 没有导入原项目 `.git`、旧环境凭证、整份数据库导出或会大量写外部 Redis 的旧测试。
- 从高级商品案例借鉴 Caffeine 本地缓存，重新实现容量、短 TTL 和提交后失效；没有直接引入缺少环境依赖的整套 Canal/OpenResty 链路。
- 前端以新的 Vue 3/TypeScript 工程实现业务交互，没有打包旧版第三方压缩脚本。
- 外部项目主要提供设计参考，源码来源与范围另见 `THIRD_PARTY_NOTICES.md`。

## 业务模块与权限

| 模块 | 核心对象 | 服务端规则 |
| --- | --- | --- |
| 账号 | 用户、验证码、Token | 验证码一次性消费，发送间隔控制，退出后撤销 Token |
| 商家 | 商家、成员、门店授权 | 从当前登录用户解析成员身份；请求参数不能直接授予商家或门店权限 |
| 活动 | 优惠券、库存、开始结束时间 | 仅所属商家有权限发布，活动审核与变更规则分阶段补齐 |
| 订单 | 预约、订单、状态变更 | 库存与落单同一事务，业务唯一约束兜底；仅本人或授权商家可查询 |
| 核销与售后 | 核销码、核销记录、退款单 | 根据当前身份解析门店范围；条件状态更新处理重复核销及退款竞争 |
| 审计 | 操作人、商家、门店、资源、动作 | 从服务端上下文记录，不信任前端传来的操作人和商家身份 |

当前已实现只读商家工作台：OWNER/MANAGER 可见本商家门店；STAFF 只见显式授权门店，即使错误地给了其他商家的门店授权，也不能越过商家边界。成员管理、活动发布、核销与审计写入仍待实现，原有商铺/券写入口暂时返回 403。

社区发布、点赞和关注写入口也暂时关闭，后续以白名单请求 DTO 和并发一致性测试逐步开放。关闭策略同时在实际匹配路由和控制器执行，包含矩阵参数、编码路径的回归验证。

## 抢购与订单状态

1. 请求经过登录校验，服务端检查活动存在及时间窗口。
2. Lua 检查库存和领取记录，原子预扣、写入有归属的预约状态并追加 Stream 消息。
3. API 返回字符串订单 ID，含义为已受理；前端进入 PROCESSING，不直接宣布成交。
4. 独立事务服务创建数据库订单并扣减数据库库存，依靠主键和 `(user_id, voucher_id)` 唯一约束处理重投。
5. 确认持久化结果后，更新状态并确认正确的 Stream 消息。失联消费者的 pending 消息可在空闲阈值后接管。
6. 确定业务拒绝才执行一次性库存补偿；连接/提交结果未知时保留预约，并将异常消息留给对账处理。
7. 前端按本人订单 ID 查询，采用有上限的轮询并支持离开页面停止查询、刷新恢复。查询超时展示结果待确认。

当前消费者为每实例一个线程，重试上限 5 次，失联接管空闲阈值 60 秒，预约状态保留 24 小时。MySQL 中已创建订单仍可按本人身份查询。主链路逐次查数据库验证活动时间，是后续压测需要观察的成本。

Redis Lua 在本实例内原子执行不等于跨 Redis/MySQL 的分布式事务。AOF everysec 仍存在故障丢失窗口；Redis 数据丢失后从数据库补库存也不能自动恢复全部预约。当前不声称 exactly-once、零丢单或任意多实例扩容。

## 前端建设

- 用户区：登录、店铺列表/详情、活动与库存状态、抢购提交、订单状态查询。
- 商家工作台：先显示真实角色与授权门店，再接活动表单、核销与售后列表。
- 将订单 ID 等 64 位标识视为字符串，避免 JavaScript 数值精度损失。
- API 层统一处理业务错误、网络错误与 401；前端权限控制负责体验，最终权限由后端校验。
- 下一阶段观察按需加载、列表分页、轮询退避、重复请求合并和页面加载表现。

## 分阶段验收

### 阶段一：可运行基线（本次）

已有前后端工程、环境配置、SQL 演示数据、登录与商铺、异步订单基础、商家门店查询、关键测试和 CI。

验收：后端测试/打包、前端类型检查/构建通过；真实 MySQL+Redis 环境中跑通 HTTP 冒烟。真实服务验证结果单独记录，编译成功不替代联调结论。

### 阶段二：完整业务演示（下一优先级）

- 商家发布/上下架活动，校验角色和门店归属，提交后预热活动数据。
- 用户订单列表、开发模拟支付、到店核销；支付能力与真实资金通道明确分开。
- 核销幂等、退款与核销条件互斥、取消库存回补、操作审计。
- 商家 OWNER/STAFF 两种账号完成同一笔订单的演示；跨商家、跨门店越权测试通过。

### 阶段三：并发与故障证据

- 测量商铺热点查询与集中抢券；记录吞吐、P95/P99、错误率、数据库连接、Redis 延迟与消息积压。
- 并发账号和重复请求分开建模；最终检查数据库库存、唯一订单数及预约差异。
- 演练重复投递、数据库短暂中断、消费者退出、ACK 失败；开发对账、人工重放与补偿操作页。
- 比较开启/关闭 Caffeine、活动元数据缓存、消费者数量等单一变量，不捏造性能数字。

### 阶段四：产品扩展

售罄订阅、取消回流后的候补递补、经营统计和异步导出按剩余时间加入。Canal 缓存同步、Redis 高可用部署可作为独立实验，避免阻塞核心演示。

## 项目问答准备

每个实现保留“需求、选择、失败场景、验证证据”四部分。重点准备事务回滚与唯一约束、Redis Lua 的原子边界、pending/ACK、幂等补偿、缓存一致性、轮询体验和服务端数据权限。算法、Java/JUC、MySQL、网络与操作系统的准备单独安排。
