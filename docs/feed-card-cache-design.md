# Feed 公共卡片缓存与回源合并设计

2026-10-30，用户已确认纳入本轮缓存亮点。状态、任务和依赖只在[STATUS](../STATUS.md)维护；本文定义CAP-07的行为与验收，**不是已交付能力或压测成绩**。先完成CAP-06长尾定位修复，再实现本文，复用CAP-07既有A/B、有限阶梯和独立核验，不另开一轮性能工程。

## 目标与现状

交付一条真实`GET /feed/notes`读取链路：当前关系/公开事实和游标目录 → 公共内容L1/Redis批量读取 → miss批量回源及同进程singleflight合并 → 个人状态与公共计数装配。保持既有HTTP路径、响应字段、字符串ID、时间格式、分页和`source=database/projection`语义。

目前Feed完整SQL已读取正文与计数；公共计数`GetMany`使用MGET/IN，单键`Cache.Get`的回源合并仅有组件/真实依赖测试，未接入详情HTTP。只把flight套在计数补读上不能称完整Feed缓存优化。本文将正文等共享内容从目录查询拆出，使内容缓存实际代替内容加载，而不是查完完整正文后再读缓存。

首版不增加页ID缓存、个性化整页共享缓存、动态hotkey、热榜、收藏、内容编辑/下架API或新的中间件。点赞事实、计数与Kafka投影规则保持。新代码使用现有Go/Redis/MySQL栈；如使用`golang.org/x/sync/singleflight`，沿用go.mod已锁定版本，不顺带升级工具链/依赖。

## 数据与缓存边界

| 数据 | 来源与规则 |
| --- | --- |
| note ID、作者、当前关注、公开状态、发布版本、发布时间、页顺序/游标 | 现有SQL事实和RR目录；不能让缓存或延迟Kafka投影替代当前事实过滤 |
| 门店ID/名称、本人`likedByMe` | SQL目录/批量个人查询；店名不受笔记发布版本控制，不塞入卡片缓存 |
| `title/content/images` | 可共享的公共卡片片段，批量缓存与加载；不含用户身份、权限、动态计数、整页JSON或游标 |
| `liked/comments` | 既有独立公共计数缓存/目录回退；点赞不递增笔记发布版本，因此不能并入内容卡片 |

建议键为`community:note-card:v1:<noteID>:<publishVersion>`，`v1`只代表缓存格式版本。payload携带格式版本、十进制字符串ID和发布版本，读取后逐项校验，坏JSON/错误类型/ID或版本错配按miss处理；返回前按原目录顺序组装，不依赖MGET/SQL返回顺序。共享切片/对象不得被某个请求修改而污染其它请求。

L1必须同时有条数和内容字节预算，Redis键有TTL及受限抖动；实现前固定并记录TTL、L1预算、单卡大小、batch大小、inflight/并发加载上限和共享加载超时。可沿用现有2秒L1、60秒Redis及0–15%抖动作为起点；若新内容缓存选择不同值，A/B与冷热实验协议保持并落证，不改变已有计数TTL来掩盖CAP-06问题。超大卡片可不缓存并正确返回，不能截断正文或拒绝原本合法的业务内容。

版本键表示同一发布版本的内容不可变。未来任何合法正文/图片变更必须同步递增发布版本；当前只有发布/详情，无需为缓存增编辑接口。新请求由SQL目录读到新版本，不再访问旧版本键，旧命名空间由TTL回收。旧加载可以完成在旧版本命名空间内，但不能写入新版本或无版本的“当前内容”键；不宣称失效后旧键物理上绝不会重建。若实现另有同版本失效/重建，则必须给出相应代次栅栏，避免旧加载回写。

## 读取流程与并发变化

1. 在现有事实快照内查询窄目录：保留作者集合、当前关系EXISTS、公开状态、可用投影与完整性回退、`(create_time,id)`排序及limit。取所需ID/发布版本/元数据、计数回退值、门店名及本人点赞；不再读取`title/content/images`。目录为空时直接按现契约返回。当前app始终调用`WithProjections()`，即使Kafka关闭/响应`source=database`，仍在RR中执行事实回退；不能把source误当内部开关。显式未启用projections的Service原本可直读，若要统一该路径的事务语义，需独立变更并让A/B两侧一致，不能混入缓存收益。
2. **提交只读事务、归还连接后**才访问卡片缓存、等待flight或执行内容批量SQL。缓存对象只持安全池和应用生命周期，不绑定事务或Gin/用户context，避免再次嵌套借池。
3. 批量读L1和Redis；同批缺失集合进入下面的flight。赢家在执行SQL前再查一次缓存，避免前一个加载刚完成时重复回源。一次`IN`/等价批量SQL取缺失内容，并按请求中的`(ID, publishVersion)`和`PUBLISHED`逐项匹配，不能把新正文配到旧版本目录。
4. 按原目录装配公共片段、个人状态与独立计数。卡片缓存命中不跳过事实查询；仍有SQL，收益主要验证内容加载、传输/解码与冷突发成本，不预设总SQL为0或QPS翻倍。

暖缓存v1命中可以服务已建立的v1 RR快照，与现有请求读快照语义一致；不承诺响应发出瞬间最新。下一请求仍重新检查关注、公开事实与版本。

若冷加载期间版本改变/撤回而缺少目录要求的内容，不能填空卡、静默缩页、错配正文或跳过游标。首版采用**至多一次既有全字段Feed的新RR回退**：新增或复用一个不调用cache的全字段读取函数，重新读取当前完整页及个人状态，保持原输入游标；不能递归调用已经走缓存的Feed。回退仍失败就按既有错误契约有界失败，不能无限重试。Redis不可用/坏值按miss走同一受控SQL加载；MySQL错误不能缓存空内容或伪造200。每个请求自己的缓存等待及一次回退沿用本请求剩余deadline，防止多段超时叠加；共享loader仍用应用生命周期派生的独立短timeout，不随首请求/任一等待者deadline取消。

## singleflight 的首版范围

首版选择**同一进程、同一规范化缺失batch**的回源合并：以排序去重后的`(noteID, publishVersion)`集合及格式版本生成无歧义key，不含用户token/个人字段；batch结果是ID/version到公共片段的映射，各请求自行恢复页顺序和个人状态。

- 完全相同缺失集合同时加载时共享一次批量加载；请求顺序不同但集合相同也应合并。
- `[A,B]`与`[B,C]`是不同batch，允许各自一次批量加载，B可能重复；不声称部分重叠逐key唯一、整页请求合并或跨实例全局合并。不为首版引入微批调度器。
- 保留MGET/批量SQL，不能为套单键flight将一页20项改成20次SQL，也不能使用一个固定全局flight key把无关内容串起来。
- 加入者用自己的context取消等待；共享加载从应用生命周期派生独立、有界context，不绑定首个HTTP请求。首个请求取消不影响仍在等待的请求；全部等待者退出后允许共享工作运行至短deadline，不宣称自动引用计数取消。应用关闭必须取消/收敛共享加载，不产生无限后台任务。
- 共享加载、inflight队列和并发数量有界；锁只保护内存状态，不持跨所有key的锁做Redis/SQL网络操作。不把可取消等待和版本失效语义寄希望于库名本身。

Go的[singleflight文档](https://pkg.go.dev/golang.org/x/sync/singleflight)定义的是相同key在途函数合并，它本身不是缓存；[context文档](https://pkg.go.dev/context)定义请求取消/超时，二者结合仍需上述生命周期与数据隔离设计。

## 必要验收（结果目前均待实施）

| ID | 行为与证据 |
| --- | --- |
| FC-01 真实接入 | 通过真实HTTP读同页，独立内容loader计数显示冷读一次批量内容SQL、热读内容加载0；事实/个人状态SQL仍执行。app实际注入缓存，生产Feed路径使用，不以组件测试替代业务接入 |
| FC-02 同批冷突发 | 自有fixture及受控加载延迟建立同时miss，多请求同一缺失batch仅一次批量内容加载；反序输入的相同集合可在组件边界验证规范化，无需新增HTTP排序接口，真实HTTP验证实际同批突发及页序。记录HTTP数、合并数和真实内容加载数，不把它当持续QPS |
| FC-03 不同批次与有界性 | 不同batch/部分重叠各自正确批量回源，无死锁；不要求B全局仅加载一次。不相关已命中卡片不被另一慢batch的全局网络锁拖住；缓存/加载上限与超大合法内容降级有效 |
| FC-04 个人与权限隔离 | 两用户可共享同内容但`likedByMe`不同；取消关注、新请求发现未公开/新版本、同秒跨页无重漏。事实过滤/游标和投影不完整时的SQL回退保持，不靠用户分桶缓存完整个人页 |
| FC-05 版本竞争 | 控制目录v1→冷加载前变v2/未公开，触发至多一次新RR全字段回退或明确失败；不混版本、不空卡/缩页。旧加载晚归不污染v2键，新请求不复用v1；旧版本物理键允许留待TTL回收 |
| FC-06 取消与生命周期 | 部分等待者包括首个调用者取消，其他等待者能得到正确公共结果；共享SQL/Redis慢操作按有界deadline退出，应用关闭后任务收敛。取消不破坏缓存状态或污染其它用户 |
| FC-07 降级与过期 | Redis断开、慢写、错误类型、坏payload及自然过期/冷填充仍正确有界，不以无限写缓存重试拖住正常SQL结果。数据库失败返回失败且不写空缓存；冷、热、过期后重建各有证据 |
| FC-08 比较和集成 | 受影响Go/真实MySQL/Redis回归、精确功能SHA CI/Linux race；保留既有冷计数单连接、关注/公开版本/游标与计数失效行为。固定新构建/hash、数据/配置，复用CAP-07既有A/B/持有/阶梯，不增加全站浏览器或付费AI测量 |

FC-04/05需要的内容或状态竞争可由两个真实SQL连接对自有夹具受控注入，明确是存储层回归，不将其描述为已交付编辑/下架业务。
