设计详解 / 从业务到实现

让每一次操作，
都有明确的结果。

一次消费连接用户、商家与社区。系统围绕这条业务链路组织模块，用事务保存事实，用异步任务衔接后续处理，用权限和版本约束每一次读取与变更。

01 / 一次完整消费

从活动发布，到到店履约。

用户端与商家工作台共享订单状态，取消、超时和退款也属于这条流程。

  1. 01 / 商家经营发布活动与优惠

    商家依据当前门店权限管理活动，设置库存与活动窗口；用户通过商铺分类、详情和公开优惠发现活动。

  2. 02 / 用户抢券受理请求，异步成单

    Lua 检查活动窗口、库存与用户资格，保存稳定受理映射并写入 Stream。后台事务创建订单，前端查询受理结果。

  3. 03 / 支付与关闭推进订单状态

    模拟支付进入待核销状态；用户取消或订单超时后关闭，补偿链路恢复对应预占，重复请求遵守幂等边界。

  4. 04 / 到店与售后核销、退款与审计

    有权限的门店成员处理核销和退款，事务内重查授权与订单状态；结果与操作审计一起落库。

  5. 05 / 社区发现分享体验，关注动态

    用户发布探店笔记、关注作者并点赞；关注 Feed 和公开笔记搜索帮助下一位用户发现商铺。

支付与退款为模拟资金流程。业务 AI 可辅助查询规则和订单，交易变更仍通过业务接口执行。

02 / 系统架构

三条链路，各自承担清晰职责。

后端采用 Go 模块化单体。订单使用 Redis Stream，社区使用 Outbox 与 Kafka；MySQL 保存最终业务事实。

交易：先受理，再形成可查询的持久结果

前端区分受理与成单，后台处理重复投递、未知结果与补偿。

03 / 核心设计

把可靠性落实到每个边界。

重点关注重复请求、权限变化、旧数据回流和异步处理失败。

01

抢券幂等与故障恢复

Lua 将活动检查、库存预占和受理映射放在一次原子操作中；MySQL 用事务、条件扣减与幂等检查确认最终订单。

  • 同一受理请求有稳定标识，重试可查询既有结果。
  • Stream 消息重复投递时，后台核对持久结果，避免重复成单。
  • 取消、超时或拒绝通过补偿恢复对应预占，保留受控核对与重建入口。
为什么区分“受理”与“成功”？

Redis 准入通过只表示请求已经进入处理链路。订单是否创建、状态怎样变化，以 MySQL 的持久结果为准；结果未知时保留复核状态，避免把暂时故障当作成功或直接重复业务效果。

02

逐门店权限与并发履约

OWNER / MANAGER / STAFF 的操作范围由当前成员关系和目标门店共同决定。核销与退款在业务事务内重查并锁定授权，而非只相信登录时的角色信息。

  • 同一用户在不同门店的角色独立解析，接口按目标资源校验范围。
  • 订单状态、业务版本与操作审计一起提交，处理重复及并发状态变化。
  • 成员停用或权限调整后，后续敏感操作重新检查当前授权。
工作台如何与用户订单保持一致？

两端读取同一套交易事实。商家操作受门店范围和订单状态双重约束；前端负责呈现可用动作，服务端事务负责最终授权与状态判断。

03

Feed 分层缓存与批量回源

公共正文按笔记 ID 和发布版本进入有界 L1 / Redis 缓存，缺失项批量查询并装配门店信息。同批次缺失共享加载，减少并发回源。

  • 复合游标读取 Feed 事实目录，按稳定位置继续翻页。
  • 正文、公共计数与个人点赞分别装配，避免用户状态混入共享卡片。
  • 版本检查与失效代次约束旧回源竞争，缓存失效后仍能从事实重建。
为什么不缓存完整的个人 Feed 卡片？

正文可供不同用户复用，点赞状态却依赖当前身份。把两者分开，既保留公共内容缓存收益，也保持个人状态的读取边界。

04

可靠事件与可追溯搜索

笔记、点赞和关注事实与社区 Outbox 同事务保存。Relay 投递 Kafka 后，各消费组以事件收据和业务版本处理重复与乱序。

  • 点赞使用期望状态写入，相同状态重试不重复计数。
  • 事件失败持久保存，保留定位与精确重放依据；投影与事实职责分离。
  • Elasticsearch 搜索标题与正文，支持门店筛选、PIT / search_after 分页；候选经 MySQL 复核公开状态与版本。
为什么索引命中后还要回查？

搜索索引是异步投影，可能暂时落后于发布状态或正文版本。回查当前事实可以过滤已失效候选，避免把索引存在等同于内容仍可公开返回。

04 / 技术实现

模块分工明确，源码顺着业务读。

交易、商家、社区、搜索和 AI 分模块组织，HTTP 路由、连接池与后台任务统一组装。

用户端与商家工作台

Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus；表单与列表承接交易、社区和经营操作。

API 与后台任务

Go、Gin、GORM、go-redis/v9；按模块组织处理器与业务服务，随进程生命周期管理消费与关闭。

数据、缓存与事件

MySQL 8.4 保存事实；Redis 7.4 负责 Lua、Stream 和缓存；Kafka 承接社区事件及独立消费组。

搜索与业务 AI

Elasticsearch、CJK 分词与游标分页；兼容 Chat / Embedding、Qwen、只读工具与应用层 SSE。
