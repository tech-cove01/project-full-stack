# CAP-10-CLAIM-1：活跃 Outbox 领取访问路径

## 证据与范围

S5 的800/s、60秒完整窗口为48000次实际变更，客户端调度违规和业务差异均0，API P95/P99为53/95ms；完整链路因Outbox增长44167条且60秒未恢复而失败。其约131秒SQL采集包络（包括PTS启动和尾声）中，Claim执行4261次、累计47.00秒，每次平均11.03ms、检查21380行；真实EXPLAIN使用PRIMARY顺序扫描。该包络不是恰好60秒，不能把SQL全局计数直接当主窗吞吐，也未单独量化Kafka等待。

只做一个逻辑优化：014迁移生成`claim_active`虚拟列和`(claim_active,id)`索引，Go领取查询增加等价活跃条件并明确使用该索引，跳过DONE/NEEDS_REVIEW历史。保留原时间条件、全局id顺序、SKIP LOCKED、30秒租约、attempt栅栏、重试上限、单relay、同步Kafka确认、持久化和连接池。新增索引会增加状态更新的索引维护成本，以同档负载核验净效果。

## 小票与验收

- CAP10-CLAIM-SEM：独立空数据库上的状态过滤、过期租约、跳锁和释放后领取，既有Kafka发布/重试上限集成及相关普通测试/vet通过；不能指向CAP10主库，因为Claim会领取库内任意待办。
- CAP10-CLAIM-PLAN：部署前后保留执行计划和SQL增量，确认新索引与扫描行数变化，完整业务对账后再开下一压力窗。
- CAP10-CLAIM-AB：S5失败原件和超时恢复保持；S6以同800/s×60秒、诊断关闭、同512关系分布、工具/PTS/资源作唯一对照。事件历史自然增长并保留，不通过删除历史制造相同基数。
- CAP10-CLAIM-FINAL：S7按最终版本选档，S8唯一候选，最多H1/H2同档各180秒；原8短窗/2正式与840秒上限不增加。新源码的真实CI通过才可冻结正式组。API本来已经接受800次变更/秒，优化收益应按SQL扫描、relay消化、积压和恢复衡量，不能写成HTTP从55提升到800。

## 上线与回退

先应用版本化014，再启动引用该索引的新二进制。旧二进制兼容新增列与索引；回退先换旧二进制，推荐保留增量schema。若未来确需撤schema，另写审查后的迁移，先移除索引再列；不修改已应用014账目、不删除业务事件。
