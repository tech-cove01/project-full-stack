## 1. 产品目标与交付范围

将项目做成本地生活活动交易与商家运营平台，用一条完整演示串起前后端、异步交易和 B 端权限：

> 店主发布门店活动 → 用户浏览、抢券 → 异步生成订单 → 模拟支付 → 授权店员核销 → 店主查看订单与审计；异常分支演示取消、超时关闭和模拟退款。

实习作品重点呈现三个能力：用户端能正确表达异步结果；高并发入口能守住库存与订单约束；商家后台能限制操作权限和数据范围。每个能力都要有可复现证据。

增加与业务结合的 AI 助手：规则和 FAQ 通过 RAG 带出处回答，实时商家/活动/本人订单通过受控只读工具查询。B 端可维护本门店公开知识；模型提供解释和导航，交易由现有业务流程执行。

## 2. 技术栈保持稳定

| 部分 | 本轮选择 | 实现边界 |
| --- | --- | --- |
| 架构 | 模块化单体，一个 API，一个前端工程 | 按业务拆服务类与模块，服务拆分以后续实测需求为依据 |
| 后端 | Java 21 目标，Spring Boot 3.5.16，MyBatis-Plus 3.5.17 | 沿用锁定依赖；现有 JDK 24 可做本地构建，CI 使用 Java 21 |
| 数据库 | MySQL 8.4，InnoDB | 订单、业务状态、审计及补偿事件的持久化依据 |
| Redis | Redis 7.4 单实例，Lua，Stream | 会话、准入、预约、消息及限流；Redis Cluster 适配另立任务 |
| 缓存 | Redis + 有容量上限和短 TTL 的 Caffeine | 保留现有方案，先测量再加复杂同步机制 |
| 前端 | Vue 3、TypeScript、Vite、Router、Pinia、Element Plus | 用户区和商家区共享请求层、会话和基础组件 |
| AI（P1-D 计划） | LangChain4j + 可配置远端模型/Embedding API | 显式 Bean 接入现有 Boot 3.5；Redis 有界记忆；MySQL 保存知识和向量，应用内小规模检索 |
| 可靠投递 | 订单创建沿用 Stream；DB 变更后的 Redis 补偿使用事务 outbox | 两段链路分别处理，不将其解释为跨存储原子事务 |
| 开发环境 | Windows 原生 Java/Node + Docker Desktop 的 MySQL/Redis | 不依赖旧 Linux 虚拟机中的地址、目录或手动配置 |
| 验证 | JUnit/Mockito、真实 MySQL/Redis 联调、k6、GitHub Actions | 单测、联调、并发实验分别给结论 |

P0—P2 不新增 Kafka、RabbitMQ、Canal、OpenResty、Kubernetes、分库分表或完整监控平台。现有 Redisson 可以保留，状态竞争优先依靠数据库条件更新和唯一约束。

## 3. 已确定的最小业务规则

详细定义以 [交易设计](transaction-design.md) 为准，以下决定用于减少实现分歧：

- 一单一张券；每用户每活动同时最多一笔有效订单。未支付取消/超时后可重新购买；已支付退款后保留资格、不可重买；纯技术受理失败且确认没有订单时，可释放预约占位。
- 创建订单后的支付期限默认 15 分钟，可配置。服务端裁决截止时间，前端倒计时只用于展示。
- 支付和退款均为开发演示模拟；用户支付、取消自己的订单；OWNER/MANAGER 可在本商家范围执行模拟退款。
- 业务状态为未支付、已支付、已核销、已取消、已退款。异步处理状态 `PROCESSING/CREATED/FAILED` 单独表达，不与交易状态混用。
- 单门店活动固定库存。发布后不修改价格、库存、门店和时间；首版下架后不重新上架。销售期限与核销期限分别定义。
- 下架拒绝新的预约；已受理预约继续落单，已创建订单按原规则履约。下架成功的时点及 Redis 门控协议见交易设计。
- 取消、退款各最多回补一次库存；取消完成补偿后释放资格，退款保留资格。活动已结束时回补也不重新开放销售。
- STAFF 仅能查询、核销授权门店；OWNER/MANAGER 管理本商家活动、订单、退款。前端按钮与后端数据范围都要实现。
- 成功的业务写入与审计同一数据库事务；需要更新 Redis 的后续效果写持久化事件，重试和故障恢复可追踪。

## 4. 优先级与切分方式

| 优先级 | 交付结果 | 前端 | 后端 / B 端 / 并发 | 阶段门槛 |
| --- | --- | --- | --- | --- |
| P0 | 真实环境基线 | 页面连接真实 API | 干净库初始化、旧库迁移方案、真实 Lua/Stream 冒烟 | 环境、编译、真实依赖联调通过 |
| P1-A | 商家可发布活动 | 活动列表、表单、发布/下架反馈 | 角色与门店范围、幂等发布、Redis 初始化门控 | 发布重试不重置库存，越权无副作用 |
| P1-B | 用户交易闭环 | 订单列表/详情、模拟支付、取消、状态恢复 | 状态条件更新、到期关闭、outbox 补偿、审计 | 重复与竞争操作无重复业务效果 |
| P1-C | 商家履约闭环 | 门店订单、核销、模拟退款、审计列表 | 核销码、权限、退款与核销互斥 | 用户与店员完成同一真实订单演示 |
| P1-D | 业务 AI 助手 | 对话、真实处理阶段反馈、来源/实时结果卡片；商家 FAQ 维护 | RAG、当前身份只读工具、隔离记忆、知识版本与引用 | 有据可查、无据拒答、越权无泄露 |
| P2 | 能证明并发与恢复 | 故障等待、429、未决结果表达 | 限流、对账与重放工具、k6、故障注入、必要指标 | 验收矩阵通过，原始结果可复现 |
| P3 | 可选产品扩展 | 搜索、筛选或统计 | ES / 统计等按剩余时间选一项 | 单独验收，不挤占 P0—P2 |

按表格顺序执行，每批先打通最小纵向流程再补边界，不同时铺开多个半成品。P0 + P1 是可演示版本；P2 完成后才有高并发和故障恢复的项目证据。排期以 P0 暴露的问题校准，不承诺固定天数内完成全部扩展。

### P3：按剩余时间选择扩展

首选业务需要明确时的 ES 商铺搜索：名称/标签检索、分类与价格过滤；地理过滤按已有 GEO 能力和演示需求选择。使用独立 Compose profile 或覆盖文件，默认环境不启动 ES。

如果实施 ES：MySQL 仍是事实来源，索引可重建；商铺变更与 outbox 同事务，异步同步有重试、版本控制和可搜索延迟指标。验收覆盖停写追平后的 DB/索引比对、旧事件重投及 ES 不可用降级。中文分析器与 ES 版本需匹配；不把复杂排序、聚合、深分页、推荐系统一次性纳入。

其他候选是简单经营统计或异步导出，只选能在剩余时间内完成验证的一项。候补、订阅、真实支付、退款审批、完整平台运营后台、社区写入恢复和 Redis 集群另立后续任务。

## 5. 前后端交付细则

- 路由按需加载；列表服务端分页，筛选条件与分页联动；首版不做无限复杂表格。
- 每个页面至少处理加载、空数据、失败、权限不足和重复提交；订单页面额外处理未决与网络重连。
- 64 位 ID 全链路字符串；金额以分为单位传输，沿用支持 `number|string` 的精确展示，禁止用浮点金额做业务计算。
- API 保持现有统一响应和 `authorization` 请求头；`orderStatus` 使用真实 DTO 字段名。拟新增路由与字段见交易设计，不得将规划接口写成已实现能力。
- 服务端按用户上下文检查权限与资源归属，不接受客户端价格、角色、操作人或随意传入的商家 ID 作为授权依据。
- 浏览器验收连接真实 API。Mock 可用于页面开发，但必须在报告里单独标记。
- 每批维护迁移、接口说明、验证记录与 README 进度；README 以产品介绍为主，第三方来源维护在独立说明中。

## 6. 交付与范围控制

实现 agent 每批交付完整提交号、改动文件、迁移与启动步骤、验证命令、逐项结果、原始证据位置、未完成项和限制。`PASS / FAIL / 未执行` 分开填写；重要场景失败或缺证据时不能勾选完成。

常规实现选择可自行处理并记录；若需要改变本规范的业务规则、持久化边界或技术栈，先同步修改设计与验收，再继续依赖该变化的实现。不要为了增加组件数量推迟核心交付，也不要把本机容量外推为生产容量。

## 7. 与 OpenSpec 的关系

本次采用“先定义行为与验收、再按任务实现、最后以证据验证”的规范驱动方式。OpenSpec 是管理这类工作流的一套工具，正式初始化后会建立 `openspec/specs/` 和 `openspec/changes/` 等结构；当前仓库这组文档没有声称已初始化 OpenSpec。

为尽快交接，本轮直接使用仓库内 Markdown 规范，不新增 CLI 或生成的 agent 指令。实现 agent 无需安装 OpenSpec 即可执行。后续确需使用时，可按阶段把本方案迁移成独立 change，保持需求、任务和验收对应；不要让两套规范同时出现冲突。

参考：[OpenSpec 官方入门](https://github.com/Fission-AI/OpenSpec/blob/main/docs/getting-started.md)。
